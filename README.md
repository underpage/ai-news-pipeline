# AI 뉴스 요약 파이프라인

매일 아침 지난 24시간 뉴스를 수집하고 기준에 따라 중요한 기사를 골라 중요도 순으로 나열하고 상위 n건에 대해 3줄 요약

- **수집**: 실행 시점 기준 지난 24시간에 발행된 AI 기사를 수집해 로그에 기록
- **추출**: 후보 전체를 생성형 AI가 서로 비교해 추출 기준과 중요도 기준에 따라 목록에 올릴 기사 선정
- **요약**: 선정한 기사 중 상위 n건의 본문을 3줄로 요약하고 감성 태그 추가
- **발행**: 요약 기사와 뉴스 목록(중요도 순)을 마크다운 리포트로 저장 후 저장소에 자동 커밋


## 한눈에 보기

| 항목 | 내용 |
|---|---|
| 주제 | AI |
| 키워드 | 에이전트, 개발, 모델, 보안, 신기술, 산업, 규제 (국문·영문, 우선순위 순) |
| 실행 주기 | 매일 09:00 KST (cron `0 0 * * *`, UTC 기준) |
| 수집 범위 | 실행 시점 기준 지난 24시간에 발행된 기사 |
| 수집 건수 | 하루 상한은 `COLLECT_MAX` |
| 목록 건수 | `LIST_N`건까지, 중요도 `MIN_SCORE`점 이상만 |
| 요약 건수 | 목록 상위 `TOP_N`건 |
| 자동화 도구 | GitHub Actions (단계별 Job으로 분리) |
| AI 모델 (추출·요약) | Gemini API (`GEMINI_MODEL`로 지정) |
| 뉴스 소스 | 국내·해외 매체의 RSS (`config/feeds.yml`) |


## 파이프라인 구조

```text
[GitHub Actions 스케줄러]  매일 09:00 KST / 수동 실행(workflow_dispatch)
        │
        ▼
1. Collect    src/collect.py    RSS 수집 → 지난 24시간 → AI 기사 → 링크 중복 제거 → 상한 적용
        │                       archive/logs/YYYY/MM/YYYY-MM-DD-수집.txt
        ▼                       (0건이면 이후 단계 전체 건너뜀)
2. Evaluate   src/evaluate.py   로컬 사전 필터 -> Gemini 한 번 호출로 후보마다 항목별 점수 -> 로컬에서 합계로 목록 선정 -> 상위 기사 본문 수집
        │                       archive/logs/YYYY/MM/YYYY-MM-DD-필터링.txt, YYYY-MM-DD-점수.csv
        ▼
3. Summarize  src/summarize.py  상위 기사 전체를 Gemini 한 번 호출로 3줄 요약(영문, 국문) + 감성 태그. 실패한 기사만 다시 요청
        │                       archive/logs/YYYY/MM/YYYY-MM-DD-요약.txt
        ▼
4. Publish    src/publish.py    요약 기사 + 뉴스 목록 리포트 생성 → git commit & push
                                archive/news/YYYY/MM/YYYY-MM-DD.md, index.md
```

- 단계 간 데이터는 `archive/logs/YYYY/MM/` 폴더의 텍스트 파일로 전달
- 로그와 리포트는 같은 폴더 체계를 쓰고 날짜는 파일명으로 구분
- Job마다 러너가 달라 `archive/logs/`는 artifact로 다음 Job에 전달
- 마지막 Publish Job에서 `archive/logs/`와 리포트를 함께 커밋
- Publish 단계에서 그날의 단계별 성공·실패 건수를 `archive/stats/YYYY.csv`에 하루 한 줄로 기록
- Gemini 호출은 하루에 보통 두 번 (선정 한 번 + 요약 한 번). 실패해서 다시 보내는 호출까지 단계마다 상한이 있음 (`AGENT.md` 참고)

## 실행 방법

### GitHub Actions 실행

- 매일 09:00 KST에 자동 실행
- 수동 실행은 **Actions → AI News Pipeline → Run workflow**

| 수동 실행 입력 | 기본값 | 설명 |
|---|---|---|
| `test_mode` | `false` | `true`면 소량만 수집해 전체 흐름을 검증. 결과는 커밋하지 않고 `test-report`로 내려받기만 가능 |
| `collect_limit` | 워크플로우에 정의 | 테스트 모드에서 수집할 최대 기사 수 |

### 로컬 실행

```bash
uv sync

# 한 번에 실행
uv run src/main.py

# 테스트 실행 (소량만 수집, 결과는 archive-test/)
uv run src/main.py --test

# 단계별로 실행
uv run src/collect.py
uv run src/evaluate.py
uv run src/summarize.py
uv run src/publish.py
```

- `.env`에 `GEMINI_API_KEY` 필요
- 결과는 `archive/`에 기록됨 (GitHub에서 실행할 때와 같은 위치)
- `--test`로 실행하면 결과가 `archive-test/`에 따로 쌓이고 커밋되지 않음. 실제 기록과 중복 이력에 영향 없음
- 단계별로 테스트할 때는 명령 앞에 `TEST_MODE=true`를 붙임

**주간 요약**

```bash
uv run src/weekly.py            # 지난주
uv run src/weekly.py 2026-W40   # 지정한 주
```

**자동 테스트**

```bash
uv run pytest                   # Gemini와 매체 사이트에 요청하지 않음
```

**요약 실패 기사 다시 요약 (Gemini 없이)**

```bash
uv run src/manual_summary.py export 2026-10-01   # summary-work/2026-10-01.json 생성
# 각 항목의 prompt를 아무 LLM에 주고, 받은 JSON을 answer에 넣음
uv run src/manual_summary.py import 2026-10-01   # 검증 후 요약 로그에 넣고 리포트 다시 생성
```


## 선정 기준

- 선정 관점: AI 모델, AI 에이전트, 보안, 신기술 네 분야의 현재 상태와 방향을 파악하는 데 중요한가. 네 분야는 똑같이 중요하게 봄
- 선정 순서: 사전 필터(코드) -> 항목별 점수(Gemini 호출 한 번) -> 합계 계산(코드) -> 목록 결정(코드)
- "코드"는 Gemini를 부르지 않고 프로그램이 규칙대로 처리하는 단계

### 1. 사전 필터 (코드)

- 제목에 `exclude_title`의 단어가 있으면 제외. 단어는 분류(행사, 인사, 수상, 주가, 홍보)별로 적혀 있음 (예: 세미나, 취임, 시상식, 목표가, MOU). 영문은 단어 단위, 국문은 부분 문자열로 비교
- 남은 기사를 주제 가중치 합(`topic_weights`, 기사에 붙은 주제마다 더함)이 큰 순, 같으면 최근 순으로 정렬
- 한 매체는 `PREFILTER_SOURCE_MAX`건까지, 전체는 `PREFILTER_MAX`건까지 Gemini에 보냄
- 여기서는 중요도를 판단하지 않음. 후보 수를 Gemini 한 번에 보낼 만큼 줄이는 단계

### 2. 항목별 점수 (Gemini 호출 한 번)

- 후보마다 네 항목(파급력 `impact`, 관련성 `relevance`, 새로움 `novelty`, 근거 `certainty`)에 점수를 매김. Gemini는 순위를 정하거나 기사를 고르지 않음
- 다른 후보와 비교하지 않고 각 후보를 기준에 그대로 대어 매김 (같은 점수가 여러 건이어도 됨)
- 각 항목의 가장 높은 단계는 기준에 분명히 맞을 때만, 애매하면 낮은 쪽. 회사의 규모나 이름만으로 점수를 올리지 않고 기사가 전하는 변화의 크기로 판단
- 후보마다 제목, 출처, 발행 시각, 주제 태그, 미리보기(기사 앞부분)를 보고 매김. 주제 태그는 키워드로 자동 분류한 참고용이고, 미리보기에 없는 내용은 추측하지 않음

**합계에 들어가는 항목**

| 파급력 | 뜻 |
|---|---|
| 9~10 | 업계 전체가 대응하거나 따라가야 하는 변화 (분야마다 며칠에 한 건 나올까 말까 한 수준) |
| 7~8 | 주요 기업, 제품의 방향이 새 발표로 분명히 드러남 |
| 5~6 | 특정 분야 안의 의미 있는 진전 |
| 3~4 | 업계 일반 동향, 투자, 채용, 산업 흐름, 개인 의견 |
| 1~2 | 기술과 거리가 먼 소식 |

- 구간 안에서는 영향 범위가 더 넓거나 사실이 더 구체적이면 높은 쪽
- 9~10은 다음 중 하나일 때만: 최상위 AI 모델의 새 세대 출시, 널리 쓰이는 에이전트 표준이나 프로토콜의 새 버전, 업계 전반이 동시에 대응해야 하는 보안 사태(여러 업체의 제품이나 널리 쓰이는 공통 구성요소(라이브러리, 프로토콜)에 걸쳐 수많은 조직이 동시에 패치하거나 대응해야 하는 일), 신기술의 상용화나 표준화(업계 첫 양산, 국제 표준 확정처럼 업계가 따라가야 하는 일)
- 7~8의 예: 새 모델과 API, AI 에이전트 프레임워크나 프로토콜, 보안 위협의 새 유형이나 새 공격 기법, 널리 쓰이는 제품의 치명적 취약점이나 실제 악용, 신기술의 첫 공개나 구체적인 사양과 성능 공개
- 실제 악용 중인 취약점도 한 업체 제품의 문제라면 피해가 커도 7\~8 (거의 매일 나오는 취약점 기사가 9\~10을 차지해 다른 분야를 밀어내지 않게 함)
- 5~6의 예: 기존 제품의 기능 추가, 이용 범위나 요금 변경, 특정 제품의 취약점, 신기술의 의미 있는 진전
- 상한: 기존 서비스를 더 많은 사용자에게 여는 소식은 대형 기업이라도 6 이하
- 보안 사고는 피해 범위로 구간을 정함: 조직 한 곳이나 소규모 피해, 공격자 주장만 있는 사고는 5\~6. 여러 조직, 대규모 유출, 핵심 기반시설, 널리 쓰이는 제품이 걸린 사고는 7\~8. 9\~10은 위 9\~10의 보안 사태에 해당할 때만. 실험실 시연이나 연구 결과는 사고가 아니라 새 공격 기법으로 봄

| 관련성 | 뜻 |
|---|---|
| 5 | 그 분야의 기술 자체를 바꾸는 소식. AI 모델: 주요 모델이나 API의 새 출시. AI 에이전트: 에이전트 프레임워크, 프로토콜, 에이전트용 개발 도구의 새 버전이나 취약점, 에이전트를 노린 공격과 방어 기법. 보안: AI 모델, AI 에이전트, AI 개발 도구를 노린 공격이나 그 취약점. 신기술: 칩, 로봇, 양자 등 새 기술의 첫 공개, 상용화, 구체적인 사양과 성능 공개 |
| 4 | 그 분야의 기술 내용이 구체적인 소식 (모델의 기능 추가와 성능 평가, 에이전트 적용 사례, AI와 관계없는 제품(개발 도구와 플랫폼 포함)의 취약점과 보안 사고, 공격 기법 연구, 신기술의 연구 성과와 시연) |
| 3 | 기술 내용이 일부 있는 일반 소식 (기업 전략과 발표, 인프라 투자와 공급, 정책과 규제, 거버넌스 논의) |
| 2 | 산업, 비즈니스가 중심이고 기술 내용이 적음 |
| 1 | 네 분야와 거의 관계없음 |

- 후보는 이미 AI, 보안, 신기술 기사로 걸러져 있어, 그 안에서 네 분야(AI 모델, AI 에이전트, 보안, 신기술) 중 한 분야의 기술 핵심을 얼마나 직접 다루는지로 판단
- 어느 분야든 같은 높이의 소식이면 같은 점수 (예전에는 독자를 보안 실무자로 정해 취약점이 5, 모델 출시가 4, 신기술이 3이었고 상위 10이 보안으로 쏠렸음)
- 보안의 관련성 5는 AI 모델, AI 에이전트, AI 개발 도구를 노린 공격과 취약점으로 한정함. AI와 관계없는 취약점은 거의 매일 나와 상위권을 채우기 때문. 그래서 AI와 관계없는 보안 기사는 같은 파급력이라도 다른 분야보다 합계가 10점 낮음 (업계 전체가 대응할 보안 사태는 파급력 9 이상이라 분야 상한에서 면제됨, 4. 목록 결정 7단계)

**감점에만 쓰는 항목** (합계에 더하지 않음)

| 점수 | 새로움 | 근거 |
|---|---|---|
| 3 | 새 발표, 출시, 공개, 발견, 사고를 직접 전함 | 공식 발표나 1차 출처(업체 공식 블로그, 논문, 보안 권고, 당사자 발언. 공격자의 주장은 제외)가 드러남 |
| 2 | 이미 알려진 사안의 후속 보도나 진전 | 매체 보도이고 출처가 일부만 드러남 |
| 1 | 새 사실이 없는 해설, 정리, 회고, 의견 | 익명 소식통, 전언, 추측에 의존하거나, 공격자 같은 당사자의 주장만 있고 피해자나 제3자의 확인이 드러나지 않거나, 근거가 드러나지 않음 |

- 새로움은 Gemini가 따로 아는 지식이 아니라 후보 목록, 미리보기, 지난 목록 제목에 드러난 범위에서, 근거는 매체 이름이 아니라 미리보기에 드러난 근거로 판단
- 주장이나 의혹이라도 커밋, 공개 저장소, 보안 권고처럼 독자가 직접 확인할 수 있는 자료가 미리보기에 드러나면 근거 2 이상 (공급망 오염 의심 같은 조기 경보를 놓치지 않기 위함)
- 두 항목을 합계에 넣지 않는 이유: 상위권 후보는 거의 모두 새 발표(새로움 최고점)이고, 근거는 미리보기로는 판단할 재료가 적어 매체마다 같은 점수가 됨. 합계에 넣어도 순위를 가르지 못함 (2026-10-08~10-11 점수표로 확인)

**점수와 함께 받는 것**

- 제외 표시(`exclude`): 아래 이름 중 하나. 이 이름이 들어 있지 않은 값은 제외로 보지 않음. 제외 표시를 해도 점수는 매김
  - 관련 없음: AI, 보안, 신기술 어느 쪽과도 직접 관련이 없음 (지나가는 언급 포함)
  - 홍보: 홍보성 보도자료, 제품 광고. 업체가 자기 제품, 솔루션, 대응 체계를 소개하거나 "제시", "선보여", "강조"하는 기사로, 취약점, 사고, 수치, 고객 적용 결과처럼 따로 확인할 수 있는 사실이 없는 것 포함. 주요 기업의 새 모델이나 제품 출시는 기술 내용이 있으면 홍보가 아님
  - 행사 안내: 행사, 세미나 안내
  - 인사: 인사, 수상 소식
  - 주가: 주가, 투자 전망
  - 추측: 근거 없는 추측, 개인 의견 위주의 칼럼
- 같은 사건 표시(`dup_of`): 같은 사건은 같은 발표, 같은 공개, 같은 사고를 전하는 기사. 같은 사안의 후속 보도, 다른 각도의 분석, 관련된 다른 발표는 같은 사건이 아님. 국문, 영문 기사도 같은 사건이면 묶음. 미리보기가 더 구체적이거나 1차 출처에 가까운 1건을 기준으로 삼고 나머지에 그 기준 후보를 적음. 기준 후보는 묶음을 만드는 데만 쓰고, 목록에 남길 기사는 4. 목록 결정에서 합계로 정함
- 지난 보도 표시(`prev_of`): 오늘 이미 올린 목록과 지난 `PREV_REPORT_DAYS`일 목록의 제목(번역 제목 포함)을 프롬프트에 함께 보냄. 후보가 그중 한 기사와 같은 사건(위와 같은 기준)이면 그 기사를 적음. 다음 날 다른 매체가 쓴 같은 발표, 패치, 사고 보도가 해당. 새 사실(피해 확대, 공식 확인, 악용 시작, 새 패치)을 전하는 후속 보도는 해당하지 않고 새로움 2
- 대표 분야(`field`): AI 모델, AI 에이전트, 보안, 신기술, 기타 중 하나. 기사의 중심 사건으로 고름. 공격, 취약점, 침해, 보안 사고가 중심이면 대상이 AI나 에이전트여도 보안. 모델 출시와 성능은 AI 모델, 에이전트 프레임워크, 도구, 적용 사례는 AI 에이전트, 칩, 로봇, 양자 등은 신기술, 정책, 규제, 기업 전략처럼 네 분야의 기술이 중심이 아니면 기타. 이 밖의 값은 기타. 4. 목록 결정 7단계의 분야 상한에 씀
- 선정 이유(`reason`): 한 문장. 리포트의 중요도 옆에 실림
- 번역 제목(`title_ko`): 국문이 아닌 기사만. 원문 제목의 내용과 주어, 목적어 관계를 그대로 옮기고 핵심 사실을 빼지 않음

### 3. 합계 계산 (코드)

- 파급력, 관련성을 각각 0~100으로 바꿈: (점수 - 1) / (최고점 - 1) x 100. 파급력 1은 0, 10은 100. 관련성 1은 0, 3은 50, 5는 100
- 두 항목을 `criteria_weights`(파급력 0.6, 관련성 0.4)로 가중합 (두 항목이 모두 있고 합이 1이어야 함, 아니면 실행 시 오류)
- 새로움이나 근거가 1점이면 `penalties`에 적힌 점수(각 10점)만큼 뺌. 합계는 0 아래로 내려가지 않음
- 합계는 0~100, 소수 첫째 자리까지. 예: 두 항목이 모두 최고점이고 감점이 없으면 100
- 리포트의 "중요도 N/10"은 합계를 10으로 나눠 반올림한 값

감점이 없을 때의 합계 (파급력 / 관련성)

| 파급력 | 관련성 3 | 관련성 4 | 관련성 5 |
|---|---|---|---|
| 10 | 80.0 | 90.0 | 100.0 |
| 9 | 73.3 | 83.3 | 93.3 |
| 8 | 66.7 | 76.7 | 86.7 |
| 7 | 60.0 | 70.0 | 80.0 |
| 6 | 53.3 | 63.3 | 73.3 |

### 4. 목록 결정 (코드)

1. 같은 사건 묶음에서 제외 표시가 없는 기사 중 합계가 가장 높은 1건만 남김 (같으면 사전 필터 순서가 앞선 후보). 홍보 기사가 합계로 대표가 되어 같은 사건의 정상 기사까지 빠지지 않게 하기 위함. 묶음의 기사가 모두 제외 표시면 그 사건은 목록에 오르지 않음. 묶음의 한 기사라도 지난 보도 표시가 있으면 그 사건은 목록에 오르지 않음
2. 제외 표시가 있는 기사를 뺌
3. 합계가 `MIN_SCORE` x 10 미만인 기사를 뺌 (기본 4, 즉 40점)
4. 합계가 높은 순으로 정렬. 같으면 파급력이 높은 순, 그다음 같은 사건을 다룬 기사 수가 많은 순(여러 매체가 다룬 사건 먼저), 그다음 최근 순
5. 한 매체는 `LIST_N`의 1/4(최소 2건)까지만 올림
6. 위에서부터 `LIST_N`건이 목록
7. 목록 위쪽 `TOP_N`건(요약 자리)에 분야 상한(`field_cap`)을 적용해 순서를 바꿈. 목록을 합계 순으로 보며 요약 자리를 채우는데, 같은 대표 분야(기타 포함)가 이미 `max`건(3)이면 그 기사는 건너뜀. 단 파급력이 `exempt_impact`(9) 이상이면 건너뛰지 않음(이 기사도 분야 건수에 셈). 합계가 `min_total`(70) 미만인 기사에 이르면 더 보지 않고, 남은 자리는 건너뛴 기사를 포함해 합계 순으로 채움. 건너뛴 기사도 목록에는 그대로 남음
8. 위에서부터 본문을 수집해 `TOP_N`건을 요약. 본문을 가져오지 못한 기사는 목록에만 두고 다음 순위로 채움 (이때는 분야 상한을 다시 따지지 않음)

- 지난 보도를 빼는 이유: 같은 날 후보끼리만 같은 사건을 묶으면 다음 날 다른 매체 기사로 같은 사건이 다시 상위권에 오름 (2026-10-15, 10-16 목록 30건 중 5건씩, 상위 10건 중 2건씩)
- 매체 상한이 1/4인 이유: 1/5(30건 중 6건)일 때 상위 15위 수준 기사가 상한에 걸려 빠지고 더 낮은 점수 기사가 들어갔음 (2026-10-15, 10-16)
- 분야 상한을 두는 이유: 점수 기준을 분야별로 같게 고쳐도, 보안 사고가 많은 날은 한 분야가 상위 10건을 거의 차지함 (2026-10-20 상위 10건 중 보안 9건). 업계 전체가 대응할 일(파급력 9 이상)은 상한을 넘어도 들어감
- 면제를 합계가 아니라 파급력으로 정하는 이유: AI와 관계없는 보안 사태는 관련성이 4까지라 파급력 9여도 합계 83.3. 합계 90 기준이면 보안만 면제를 거의 받지 못함
- 같은 날 다시 실행하면 남은 자리만 채우며, 매체 상한과 분야 상한은 그 실행의 후보 안에서만 셈
- 동점을 주제 순서로 가르지 않는 이유: 키워드 주제 순서(에이전트, 개발, 모델, 보안 순)로 가르면 보안 기사가 체계적으로 밀렸음 (2026-10-10 80점 동점 11건 중 보안 기사 7건이 모두 상위 10건 밖)

## 리포트 구성

- 저장 위치: `archive/news/YYYY/MM/YYYY-MM-DD.md`, 월별 목록은 같은 폴더의 `index.md`
- **요약 기사**: 중요도 순, 3줄 요약과 감성 태그(긍정/부정/중립). 요약하지 못해도 목록에서 빼지 않고 `[요약 실패]`, `[요약 불가]`, `[요약 대기]`로 표시. 수동으로 채운 요약은 `[수동 요약]`
- **더 읽어볼 기사**: 선정한 기사 중 위에서 요약하지 않은 나머지를 중요도 순으로 한 줄씩, 제목, 주제, 출처 (순위는 전체 기준으로 이어짐). 영문 기사는 원문 제목 대신 `[번역]` 표시와 번역 제목
- 국문 기사는 국문 요약만, 영문 기사는 번역 제목과 영문/국문 요약. 영문 기사의 국문 요약은 영문 요약 세 줄을 줄별로 옮긴 번역 (요약 프롬프트의 번역 규칙)
- **주간 리포트**: 매주 월요일 지난주 요약 기사로 개요와 주요 흐름을 정리 (`archive/weekly/YYYY/`). "이번 주 기사"는 그 주에 요약한 기사 전체를 합계(0~100) 순으로, 일간 리포트의 "더 읽어볼 기사"와 같은 형식에 날짜를 붙여 실음
