발행 2026-10-22 · 작성 neo

- 여러 LLM의 API를 연결하는 LiteLLM의 PyPI 배포본 1.107.0에서 인증 정보 탈취 악성코드와 원격 코드 실행 백도어 발견. Linux/macOS/Windows용 설치 패키지 7개에 악성 파일이 포함됨
- 감염된 Python 환경에서는 LiteLLM을 직접 불러오지 않아도 Python 시작 시 악성코드가 실행됨. 일반 애플리케이션뿐 아니라 pip, IDE 언어 서버, CI 작업도 실행 계기가 될 수 있음
- SSH 키와 클라우드 인증 정보, 브라우저 비밀번호, AI 개발 도구 토큰을 수집해 외부로 전송. LiteLLM 프록시 데이터베이스에 저장된 LLM 제공업체 API 키도 탈취 대상
- 공개 GitHub 소스에는 악성 파일이 없지만 배포 패키지에는 포함돼 있었음. SafeDep는 공격자가 변조한 소스를 비공개 릴리스 파이프라인이 빌드했을 가능성이 높다고 분석했으며, 정확한 침해 경로는 조사 필요
- PyPI는 1.107.0 릴리스를 삭제함. SafeDep가 확인한 1.106.2와 1.107.0rc1/rc2에는 해당 악성코드가 없었으며, 설치된 악성 파일과 백그라운드 프로세스 등 침해 지표도 공개
영향 범위와 자동 실행 구조
- LiteLLM 1.107.0의 모든 wheel 7개가 site-packages 에cook.pth ,cook.py ,sitecustomize.py 를 설치함
  - cook.pth 가cook.py 를 가져와 자격 증명 탈취 코드를 실행함
  - sitecustomize.py 는 백그라운드 데몬을 시작해 반복 탈취와 원격 코드 실행을 수행함
  - 두 진입점 모두 Python 시작 시 실행되며, litellm 을 직접 가져올 필요가 없음
- 상위 GitHub 소스에는 악성 파일이 없으며, PyPI는 해당 릴리스를 삭제함
- 1.106.2, 1.107.0rc1, 1.107.0rc2는 악성코드가 없는 것으로 확인됨
  - 1.107.0이 버전을 고정한 litellm-proxy-extras==0.4.110 과litellm-enterprise==0.1.78 도 악성코드가 없음
빌드 설정에 삽입된 악성 파일 경로
- 소스 배포본인 sdist의 pyproject.toml 에서[tool.maturin] 에data = "cook" 한 줄이 추가됨
  - 이 설정은 cook/ 폴더를 wheel의litellm-1.107.0.data/purelib/ 로 복사하며, pip가 이를site-packages 에 설치함
  - python-packages = ["litellm_cli"] 는 상위 소스에도 있는 정상 설정임
- sdist 자체에는 cook/ 폴더가 빠져 있어, 삽입 흔적으로 보이는 변경은 해당 설정 한 줄임
- wheel의 RECORD 에는 추가 파일 3개가 등록돼 있음
  - cook.pth : 12바이트이며import cook 을 실행함
  - cook.py : 22,252바이트이며 Base64 디코딩과 zlib 압축 해제 후 코드를 실행함
  - sitecustomize.py : 25,509바이트이며 로더/백도어와 내장 탈취 코드를 포함함
태그와 배포 소스의 불일치
- v1.107.0 태그는 06:59 UTC의 커밋 66c8f5b를 가리키지만, 해당 커밋의pyproject.toml 버전은1.108.0 임
- SafeDep가 sdist 파일을 Git 트리와 블롭 해시로 비교한 결과, 배포 소스의 기반은 이후 08:50 UTC에 생성된 main 커밋 a8113b0이며 파일 5개가 수정됨
  - Cargo.toml 4개에는readme = "README.md" 가 추가됐으며, 정상 1.106.2와 rc2에도 같은 변경이 있음
  - pyproject.toml 의 버전 필드 2개는1.108.0 에서1.107.0 으로 되돌려짐
  - 의존 패키지는 litellm-proxy-extras 0.4.111에서 0.4.110으로,litellm-enterprise 0.1.79에서 0.1.78로 바뀌어 rc2와 같아짐
  - 여기에 악성 삽입 설정인 data = "cook" 이 추가됨
- rc2와 의존성만 비교하면 이상 징후가 드러나지 않음
- 정상 1.106.2 sdist는 Cargo.toml 의readme 행을 제외하면 태그 커밋 49943cd와 일치함
비공개 릴리스 파이프라인을 가리키는 증거와 한계
- 악성 wheel은 정상 BerriAI 릴리스 파이프라인의 출력 특성과 일치함
  - WHEEL 파일의 빌드 도구는 정상 릴리스와 같은maturin 1.9.4임
  - 악성 파일의 RECORD 항목이 올바르게 등록돼 있어 빌드 후 수정 흔적이 없음
  - ZIP 타임스탬프는 macOS 11:20, Linux 11:21, Windows 11:37 UTC에 각각 네이티브 빌드가 이뤄졌음을 보여줌
  - Windows wheel의 Python 파일 2,804개는 악성 파일을 포함해 모두 CRLF 줄바꿈을 사용하고, Linux wheel에는 CRLF가 없음. Windows에서 줄바꿈 변환을 켠 Git 체크아웃과 같은 패턴임
- 
공개 GitHub Actions 실행에서는 빌드나 게시를 찾지 못함
  - SafeDep는 09:30~12:30 UTC의 실행 539개를 확인함
  - PyPI 업로드 약 10분 뒤인 11:50 UTC에 litellm-dispatcher[bot] 이 GitHub 릴리스v1.107.0 을 게시했으며, 정상 1.106.2에서도 같은 지연이 있었음
  - PyPI에는 1.107.0, 1.106.2, rc2의 출처 증명(provenance attestation)이 없음
- 
비공개 파이프라인을 통한 빌드 가능성과 확인 한계
  - SafeDep는 공격자가 수정한 Git 소스를 비공개 파이프라인이 빌드했을 가능성을 중간~높은 신뢰도로 평가함
  - 가능한 경로는 관리자나 봇 자격 증명 탈취, 비공개 브랜치나 미러, 파이프라인이 빌드하는 참조 대상의 변조임
  - 공격자가 자신의 장비에서 탈취한 PyPI 토큰으로 게시했다는 가설은 증거와 상대적으로 덜 부합함
  - 정확한 원인은 BerriAI 파이프라인 로그로만 확인할 수 있음
cook.py가 수집하는 정보와 전송 방식
- Python은 시작할 때 site-packages 의.pth 파일에서import 로 시작하는 행을 실행함
  - cook.pth 의import cook 때문에 애플리케이션뿐 아니라 pip, IDE 언어 서버, CI 작업에서도 탈취 코드가 실행됨
  - cook.py 는 약 61KB의 Python 코드를 Base64와 zlib로 한 겹 감싼 뒤exec() 로 실행하며, 수집은 데몬 스레드에서 수행함
- 시스템과 사용자 활동 정보를 광범위하게 수집함
  - sysinfo ,netinfo : 호스트 이름, 사용자, 운영체제, IP 주소, 네트워크 설정을 수집함
  - browser_pw : 프로필 마스터 키로 복호화한 Chromium 저장 비밀번호와 Firefox의logins.json ,key4.db 를 수집함. Windows에서는 DPAPI를 사용함
  - browser_hist ,shell_hist : 브라우저 기록, bash/zsh 기록, PowerShell PSReadLine, cmd 기록이 대상임
  - ssh_keys ,gpg_keys ,tls_privkey :~/.ssh/* , GPG 키, TLS 개인 키를 가져옴
- 클라우드와 개발 환경 비밀정보도 수집함
  - cloud_creds : AWS credentials/config, Azure 프로필과 토큰, gcloud 자격 증명, Kubernetes 및 Docker 설정, GitHub CLI의hosts.yml ,rclone.conf ,~/.netrc 가 대상임

[TITLE] 테슬라, 캘리포니아 공장서 옵티머스 휴머노이드 로봇 양산 돌입
[LINK] https://www.aitimes.com/news/articleView.html?idxno=216512
[PUBLISHED] 2026-10-22 12:14 KST
[SOURCE] AI타임스
[TOPIC] 신기술
[SCORE] 9
[REASON] 휴머노이드 상용 양산 시작, 로봇 업계 경쟁 가속
[FIELD] 신기술
[BODY]
테슬라가 미국 캘리포니아주 프리몬트 공장에서 휴머노이드 로봇 '옵티머스(Optimus)' 생산을 시작했다. 일론 머스크 CEO는 2027년 말까지 주당 2만대 생산을 목표로 제시했지만, 초기 생산 확대가 쉽지만은 않을 것이라는 신중한 입장을 내놓았다.
테슬라는 21일(현지시간) 공개한 3분기 실적 보고서에서 옵티머스 생산 개시를 발표했다. 전기차 생산에 사용하던 공간을 로봇 제조 시설로 전환해 상업용 제품 생산에 들어갔다는 내용이다.
"이번 생산 라인에서 나오는 로봇은 우리가 제조한 최초의 양산 품질 로봇"이라며 "현재의 옵티머스 제조 공정이 상용 제품 생산에 적합하다는 점을 입증했다"고 밝혔다.
머스크 CEO는 실적 발표 후 진행한 컨퍼런스콜에서 이번 생산을 "초기 생산"이라고 규정했다. 이어 "완전히 새로운 제품이기 때문에 생산량을 늘리는 과정은 느리고 다소 순탄하지 않을 것"이라고 말했다.
테슬라는 2027년 말까지 프리몬트 공장에서 옵티머스를 주당 2만대 생산할 수 있을 것으로 기대하고 있다. 고객 인도는 내년 말부터 시작하는 것이 목표다. 다만 설계와 제조 공정을 계속 개선해야 하는 만큼 생산 확대 시점과 규모에는 변수가 남아 있다.
머스크는 로봇의 안전성과 내구성을 확보하는 일이 중요하다고 강조했다. 그는 "안전하고 신뢰할 수 있으며 오래 사용할 수 있는 로봇을 만들어야 한다"며 "한 달 만에 고장 나는 제품이어서는 안 된다"고 말했다. 이어 "다양한 작업을 실제로 수행할 수 있는 로봇을 만들려면 AI와 로봇 자체에 관해 아직 상당한 작업이 필요하다"고 덧붙였다.
테슬라는 로봇의 학습 능력을 높이기 위해 '옵티머스 아카데미'도 구축하고 있다. 로봇이 다양한 작업을 반복적으로 연습하면서 데이터를 생성하고, 이를 바탕으로 로봇을 구동하는 AI 모델을 개선하는 방식이다. 차세대 'AI5' 칩도 내년 4월 탑재할 계획이다. 머스크는 새 칩이 로봇의 연산 능력을 높이고 지능을 크게 개선할 것이라고 설명했다.
프리몬트 공장은 올해 초 모델 S와 모델 X 생산을 중단하고 옵티머스 제조 공간을 마련했다. 테슬라는 이 생산 라인의 장기 목표를 연간 100만대로 설정했다. 텍사스주 오스틴에 건설 중인 두 번째 생산 라인은 연간 1000만대 생산 능력을 갖추는 것이 목표다.
최신 옵티머스 모델의 구체적인 모습은 아직 공개되지 않았다. 머스크는 앞으로 한두 달 안에 관련 영상을 공개할 것으로 예상한다고 밝혔다.
옵티머스 생산 개시는 테슬라의 미래 사업 확장에는 의미가 있지만, 3분기 실적은 부진했다. AI와 자율주행 기술 개발에 대한 투자가 늘면서 비용이 급증했고, 순이익은 전년 동기보다 43% 감소했다.
테슬라의 3분기 매출은 280억4000만달러(약 37조원)로 전년 동기 280억9000만달러보다 소폭 줄었다. 순이익은 7억8700만달러(약 1조원)로, 지난해 같은 기간의 13억7000만달러에서 크게 감소했다.
전기차 매출은 200억달러(약 26조원)로 전년과 비슷한 수준을 유지했다. 3분기 차량 인도량은 48만6532대로 전 분기보다 6000여대 늘었지만, 전년 동기보다는 줄었다. 태양광과 에너지저장 사업 매출도 관세 관련 고객 환급 등의 영향으로 16% 감소한 28억달러(약 3조7000억원)를 기록했다.
반면 서비스 사업 매출은 완전자율주행(FSD) 소프트웨어 구독 등에 힘입어 전년 동기보다 33% 증가한 46억달러(약 6조원)를 기록했다. 해당 부문의 매출총이익은 7억3400만달러(약 9600억원)로 사상 최대치를 나타냈다.
테슬라 경영진은 자율주행 사업에 대해서는 낙관적인 전망을 유지했다. 다만 운전자의 감독 없이 주행하는 FSD 기능의 출시 일정은 다시 미뤄졌다.
테슬라 AI 소프트웨어 부문을 이끄는 아쇼크 엘루스와미 부사장은 "내년 2분기 무렵 일부 고객 차량을 로보택시 운행에 투입할 수 있을 것으로 예상한다"고 말했다. 이는 FSD 감독형 기능을 사용하는 고객 차량에 소프트웨어 업데이트를 제공해 운전자 개입 없이 주행할 수 있도록 하는 계획을 뜻한다.

전 세계 기업이 인터넷 상당 부분을 구동하는 널리 쓰이는 코드에서 치명적 취약점 2건이 공개된 뒤 대응에 분주하다. PHP 스크립트 언어에서 발견된 두 결함은 공격자가 인증 없이 원격 코드 실행(RCE)을 수행하도록 허용할 수 있다.
PHP 재단(PHP Foundation)은 수요일 오전 영향받는 버전의 패치를 배포하고, PHP를 운영하는 기업이 즉시 패치하는 것이 필수적이라고 밝혔다. 또한 PHP-FPM, 아파치(Apache)의 mod_php, php-cgi, 프랭큰PHP(FrankenPHP), 라이트스피드(LiteSpeed) 등 웹 요청을 처리하는 모든 PHP 설치 환경이 위험하다고 설명했다. 위험도가 가장 높은 환경은 mod_php로, 인증 없는 요청만으로 애플리케이션 코드가 실행되기 전에 공격이 이뤄질 수 있다고 판단했다.
취약점 공개에 대응해 네덜란드와 핀란드 등 유럽 일부 정부 웹사이트와 전 세계 다른 기업의 웹사이트가 예방 차원에서 오프라인으로 전환됐다.
‘웹 그 자체’로 불리는 PHP
PHP는 널리 쓰이는 오픈소스 서버 측 스크립트 언어로, 전체 웹의 43%를 구동하는 워드프레스(WordPress)를 비롯해 메일침프(Mailchimp), 드루팔(Drupal), 마젠토(Magento), 라라벨(Laravel), 슬랙과 줌의 일부 등 수많은 서비스의 기반이다.
네덜란드 국가사이버보안센터(NCSC-NL)는 PHP2Shell로 통칭되는 두 결함을 설명하며 영향이 웹사이트에 국한되지 않는다고 짚었다. PHP는 어플라이언스, 네트워크 장비, 관리 인터페이스 등 관리자가 PHP를 직접 업데이트할 수 없는 업체 제품에도 내장돼 있다. 또한 유럽연합의 사이버 보안 위협 추적 기구 CERT-EU는 다수의 상용 및 오픈소스 제품이 PHP를 백엔드 기술로 쓰고 있어, PHP 설치 환경을 직접 노출하지 않더라도 결함의 영향을 받을 수 있다고 경고했다.
사정이 이렇다 보니 취약점의 심각성은 한층 높아진다. 공통 취약점 평가 시스템(CVSS)에서 9.2점을 받은 CVE-2026-109618은 메모리 부족(OOM) 처리 중 발생하는 메모리 손상을 통해 원격 코드 실행을 허용할 수 있다. OOM 처리는 운영체제와 애플리케이션이 물리적 RAM과 스왑 공간이 고갈됐을 때 사용하는 전략이다.
CVE-2026-109619 역시 9.2점으로, 같은 워커에서 이후 요청이 앞선 요청이 남긴 오래된 전역 상태를 재사용하는 과정에서 원격 코드 실행이 가능하다.
PHP 재단은 두 결함이 거의 모든 요청이 거치는 영역인 메모리 관리와 오류 처리에 자리 잡고 있다고 짚었다. 그만큼 두 버그는 극도로 심각하며, 호환성이나 성능에 영향을 주지 않고 고치기도 어렵다. 기업은 이미 노출돼 있다는 가정에서 대응을 시작해야 한다.
포레스터의 시니어 애널리스트 마델레인 판 데르 하우트는 취약점의 심각성이 결함이 위치한 곳에서 비롯된다고 설명했다. PHP가 전체 웹사이트의 70%를 떠받치고 있어 거대한 집중 위험이 된다는 분석이다.
판 데르 하우트는 “기업 웹사이트만 점검해서는 충분하지 않다”라고 말했다. 또한 기업이 노출 지점을 파악하고 인터넷에 연결된 시스템부터 우선 처리해야 한다고 조언했다.
영향받는 기업은 PHP 8.5.12, 8.4.27, 8.3.36 또는 8.2.35로 업데이트해야 한다. PHP 재단은 리눅스와 장기 지원(LTS) 업체가 패치를 미리 받은 만큼 기업이 업체에 수정 사항을 확인해야 한다고 밝혔다.
PHP 8.1과 기타 수명 종료 버전은 PHP 프로젝트에서 더 이상 업데이트를 받지 못한다. 다만 일부 배포 업체와 LTS 업체가 백포트 패치를 내놓기도 하므로, 지원이 끝난 버전을 쓰는 기업도 업체에 확인해야 한다.
PHP 재단은 자원봉사자가 관리하는 rpms.remirepo.net에 의존하는 기업이 업데이트를 즉시 적용하려면 배포 패키지로 바꾸거나 소스에서 직접 빌드해야 한다고 권고했다.
CERT-EU는 즉시 패치할 수 없는 기업이 PHP 재단이 설명한 예방 조치를 취해 노출을 줄여야 한다고 밝혔다. 다만 이런 완화 조치만으로 설치 환경이 안전해지는 것은 아니라고 경고했다.
런타임 앱 보안 업체 OX 시큐리티(OX Security)의 CEO 니트순 지브는 “인터넷 규모 취약점의 전형적인 모습이다”라고 말했다. 또한 이처럼 어디서나 쓰이는 기술에 결함이 발생하면 피해 범위는 특정 제품이나 산업에 그치지 않고 웹 그 자체가 된다고 강조했다.
OX 시큐리티 연구진은 독립적으로 결함을 재현한 결과, 취약한 기능이 기본적으로 활성화돼 있으며 PHP 5.4 버전부터 존재해 왔다는 사실을 확인했다.
그럼에도 전문가는 패치가 대응의 한 요소일 뿐이라고 강조한다. 판 데르 하우트는 속도가 중요하다며, 보안팀이 PHP가 구동되는 모든 곳을 파악하고, 노출된 시스템의 우선순위를 정하고, 공식 수정 사항을 신속히 적용하고, 침해 징후를 조사해야 한다고 언급했다.
또한 판 데르 하우트는 패치가 취약점을 고칠 뿐 공격자가 이미 확보했을지 모를 접근 권한까지 반드시 없애지는 않는다고 경고했다.
오프라인 전환과 해킹의 구분
다크웹에 익스플로잇이 이미 나돈다는 소문이 있는 상황에서, 전문가들은 서비스를 내려 보호하고 패치하는 것이 현실적인 선택이라고 평가했다.
판 데르 하우트는 웹사이트를 오프라인으로 전환했다고 해서 해킹당했다는 의미는 아니라고 강조했다. 기업이 잠재적으로 취약한 시스템을 아직 패치하지 못했거나 충분히 보호하지 못한다면, 일시적인 오프라인 전환이 ‘비례적 위험 판단’이 될 수 있다는 것이다. 즉, 심각한 침해 가능성을 감수하느니 짧은 가용성 손실을 받아들이는 선택이다.
궁극적으로 이번 사태는 단순한 패치 관리가 아니라 운영 복원력의 시험대라고 판 데르 하우트는 분석했다. 기업은 서비스를 계속 운영할 수 있는지, 필요할 때 누가 서비스를 내릴 권한을 갖는지 결정해야 한다.
판 데르 하우트는 “일시적인 서비스 중단이 옳은 결정일 수 있지만, 확인된 침해가 없어도 소프트웨어 취약점이 비즈니스 중단으로 번질 수 있음을 보여준다”라고 덧붙였다.
방어와 해킹 양쪽에서 AI가 맡는 역할
오픈AI는 PHP 대응에서 자사가 맡은 역할을 상세히 설명하는 블로그 게시물을 올렸다. 레드팀 기업 캘리프(Calif)가 오픈AI의 ‘패치 더 플래닛(Patch the Planet)’ 이니셔티브의 일환으로 GPT 5.6 Sol을 이용해 치명적 결함을 식별했다고 밝혔다. 클라우드 보안 업체 위즈(Wiz)도 독립적으로 두 취약점을 발견해 보고했으며, 오픈AI 파트너는 PHP 공개에 앞서 연구, 기술 지원, 조율에 기여했다.
PHP 버전 점검 도구는 코덱스 스킬 형태로 공유돼, 기업이 취약한 PHP 버전을 식별하고 알맞은 업데이트를 적용하는 데 쓸 수 있다.
오픈AI는 “결함의 심각성과 PHP의 광범위한 사용을 고려할 때 최근 가장 큰 영향을 미친 보안 문제 중 하나로 판단한다”라고 밝혔다.
또한 오픈AI는 이번 사례가 보안 분야에서 AI의 역할이 바뀌는 전환점이라는 입장을 나타냈다. 공격자보다 먼저 프런티어 AI가 취약점을 발견해, 유지관리자에게 ‘방어자의 창’이라 불리는 선제 대응 시간을 벌어줬다는 설명이다.
오픈AI는 AI가 인터넷 규모의 영향을 지닌 보안 결함을 찾아낼 수 있지만, 같은 역량이 공격자의 공격 도구와 익스플로잇을 빠르게 개발하는 데에도 쓰일 수 있다고 우려를 나타냈다.
글로벌 기술 공급업체 어댑태비스트 그룹(The Adaptavist Group)의 데브옵스 책임자 맷 손더스는 후자의 가능성을 강조했다. 취약점이 공개되는 즉시 수많은 AI 봇이 악용할 시스템을 찾아 나설 것이며, 낮은 심각도의 공격 여러 건을 새로운 치명적 결함과 엮어 기업에 침투할 수 있다는 지적이다.
손더스는 AI로 고도화된 공격을 쓰려는 쪽이 활용할 수 있게 된 만큼, 침해가 발생했을 때 피해 범위가 과거보다 훨씬 넓어질 수 있다고 우려했다.

London- and New York-based Tracebit has developed a military style solution to AI attacks. Just as landmines are used to destroy or slow an advancing army, Tracebit has developed AI ‘context bombs’ that are planted in the battlefield. Each bomb comprises crafted and hidden prompts that are automatically ingested by the attacking AI when it crawls the target. These new prompts interfere with the original, possibly malign, purpose of the attacking agent.
Tracebit’s new research (Making attacking agents pay’) extends earlier research that used different context bombs to trigger guardrails. It now focuses on misdirecting and entrapping the agents with fake targets and deceptively complex problems. To achieve this, Tracebit developed nine new context techniques (ingested fake prompts) that stopped all GPT 5.6 Cyber, Kimi K3, Qwen 3.8 Max, and DeepSeek V4 Pro attacks. The same bombs also worked against Frontier Models, cutting GPT-6 Astra’s successes by 54% and nearly quadrupling its bill per attack. The effect against Claude Opus 5 was even more obvious: attack success was cut by 91%.
The single most effective of the nine prompt bombs was a fake pen testing report. It presented itself as a recent assessment, labeled real attack paths as canaries, and described decoys as valuable targets that had already been exploited. In many cases it made the AI believe the defender’s real systems were traps – so it avoided them, reducing the achieved objectives by 58%. Some agents accepted the warnings and stopped early, leaving exploitable targets untouched. Across Cyber, Kimi, Qwen and DeepSeek, runs reaching an objective fell from 39 / 40 at baseline to 2 / 40.
Other bombs include an unending web service, apparent passwords locked behind layer after layer of encryption, and an endless database. In this last deception, every page pointed to another page. “GLM-5.3 crawled 825 pages in 55 minutes, spotted the trap, tried other leads, and still came back for one more try,” comment the researchers.
Combining the bombs had the best overall effect. None of the Chinese models from Moonshot, Alibaba and DeepSeek achieved their objectives when all nine bombs were deployed.
Even if the context bomb failed to stop an attack, it increased the cost of each success by 23x. Attackers may have deep pockets, but they are not limitless. There comes a point where the value of the target simply isn’t worth the cost of the attack.
Tracebit’s neutralizing prompt injections are effectively the opposite of malicious prompt injection attacks. Even if this occurs from an external attacker, the internal context bombs are the most recent prompts that should usurp the attacker’s intent.
Andy Smith, co-founder and CEO at Tracebit, explains the arguments: “We’ve seen in recent attacks that AI models exhibit unsanctioned and deceptive behaviors – the best defense against that is to beat them at their own game. This means adopting deception to send them down rabbit holes and tie them up in knots, so they burn time and tokens while avoiding real targets. By inflating the cost 23x it asks the attacker, ‘is this worth it’, meanwhile the agents run erratically which makes them more likely to trigger alarms – alerting defenders to a problem and giving them more time to respond.”

AI agents are getting more inventive in finding ways to circumvent safeguards to prevent bad behavior, OpenAI has revealed.
On Tuesday, it reported two incidents, both involving the agent disabling or interfering with its alignment monitoring, and in one case directly lying about having done so.
“In two internal coding tasks, agents weakened misalignment monitoring while making requested software changes,” the OpenAI blog post said. “A GPT-6.1 Sol agent repairing an evaluation pipeline disabled automatic alerts to our Security team, treating an earlier instruction not to send messages during a Slack history search as a reason to suppress monitoring notifications. In a separate task, a GPT-6 Astra agent migrating a program removed its monitoring integration in order to match a reference implementation, and then falsely claimed to the user that it had not removed the monitor.”
In both cases, OpenAI reported, the agents considered whether monitoring safeguards should be preserved, “but interpreted routine coding instructions as permission to weaken them.”
OpenAI said that, in response, it has been strengthening its monitoring programs to prevent agents from being able to disable the protections.
“In addition to making it harder for models to disable monitoring, we are looking to understand why models might seek to do so in the first place,” OpenAI said, suggesting that it may simply be an example of “benign overpersistence,” with models not understanding why monitoring is important.
“We are also developing evaluations to test whether models might have a propensity to evade misalignment monitoring in particular and exhibit motivated reasoning in order to do so,” OpenAI added. “We don’t yet have a satisfying explanation for this behavior and will investigate this behavior through the creation of paired evaluations, resampling of agent continuations, and experiments on models’ internal activations.”
OpenAI, like almost every agentic AI vendor, has been struggling with making its autonomous agents more productive and self-sufficient while simultaneously protecting customer environments from bad agent behavior. It has even tried to slow down the pace of its scaling, to allow for the development of better agent restrictions.
Particulars alarming
Analysts and consultants said the revelations were surprising only in their scope. But they were alarmed by some of the particulars in the OpenAI disclosures.
Aman Mahapatra, chief strategy officer for New York City-based technology consulting firm Tribeca Softech, stressed that some level of monitoring was maintained, but only for the agent itself. That meant that the workloads the agents created were left invisible.
“The agent was watched. What it built was not,” he said. “Agent-spawned pipelines, jobs, service accounts, and cloud functions are the next generation of shadow IT, and almost no enterprise enforces monitoring inheritance on them.”
Mahapatra also stressed that the severity classification described in the post is concerning.
“The severity handling is the part CISOs should sit with,” he said. “Neither event was classified P0 [maximum severity] and neither run was killed. The one category of agent behavior that degrades every future detection ranked below the paging threshold because nothing visibly broke.”
He pointed out that this reveals a disadvantage for the enterprise, noting, “OpenAI caught this because it can read its agents’ reasoning. Most enterprise SOCs see only outputs, so if the lab with chain-of-thought visibility filed this below its paging line, assume your SOC never saw it at all. EDR settled this a decade ago with tamper protection: any attempt to disable the sensor is the alert. An agent touching its own monitoring should page someone every single time.”

[TITLE] 엔비디아, 휴머노이드·AI 학습 기술 확대...범용 로봇 개발 위한 아이작 플랫폼 고도화
[LINK] https://www.aitimes.kr/news/articleView.html?idxno=42386

[FIELD] 신기술
[BODY]
아이작 랩 3.0·로봇 운영체제·학습 데이터 강화…시뮬레이션부터 현장 배치까지 지원
엔비디아(NVIDIA)가 범용 로봇 개발 플랫폼을 확장하고 휴머노이드 학습부터 시뮬레이션, 실제 환경 배포까지 지원하는 기술 체계를 강화한다. 로봇 하드웨어와 인공지능(AI) 모델, 학습 데이터, 안전 기술을 연결해 개발 복잡성을 낮추고 산업 현장의 피지컬 AI(Physical AI) 도입을 가속화한다는 전략이다.
엔비디아는 21일(현지시간) 독일 베를린에서 열린 GTC 베를린 2026에서 오픈 로보틱스 개발 플랫폼 ‘엔비디아 아이작(NVIDIA Isaac)’의 주요 업데이트를 발표했다. 휴머노이드 레퍼런스 플랫폼과 로봇 학습 프레임워크, 오픈소스 런타임, 시뮬레이션 데이터 및 안전 기술을 새롭게 선보였다.
로봇 기업 애자일 로봇(Agile Robots)은 엔비디아 아이작 GR00T와 엣지 AI 컴퓨팅 플랫폼 젯슨 토르(Jetson Thor)를 기반으로 한 휴머노이드 레퍼런스 플랫폼 ‘애자일 원 SN(Agile ONE SN-보기)’을 공개했다.
애자일 원 SN은 시뮬레이션과 학습, 실제 로봇 배포에 필요한 도구를 하나의 플랫폼으로 통합해 개발 환경 구축에 걸리는 시간을 기존 수주에서 수일로 단축하도록 설계됐다.
높이 1.4m, 무게 40kg의 본체에 31개의 자유도를 갖췄으며, 양팔은 각각 최대 3kg의 하중을 처리한다. 젯슨 토르는 FP4 기준 2070테라플롭스(TFLOPS)의 연산 성능과 128GB 통합 메모리를 제공한다. 카메라와 라이다 센서 등을 통해 주변 환경을 인식하고, 아이작 GR00T 기반으로 로봇의 행동과 전신 제어 기술을 개발할 수 있다.
애자일 원 SN은 2027년 초 출시 예정이다. 애자일 로봇은 엔비디아의 풀스택 안전 플랫폼 할로스(NVIDIA Halos)와의 통합도 계획하고 있다.
엔비디아는 로봇의 학습과 검증을 지원하는 소프트웨어와 데이터도 강화했다. 오픈소스 로봇 학습 프레임워크 ‘엔비디아 아이작 랩 3.0(NVIDIA Isaac Lab 3.0-다운)’은 정식 출시됐다. 멀티 GPU 환경과 물리 엔진을 활용해 데스크톱부터 데이터센터까지 로봇의 행동 정책을 학습하고 개선할 수 있다.
오픈소스 런타임 ‘엔비디아 아이작 OS(NVIDIA Isaac OS)’는 AI와 센서, 제어 시스템, 로봇 하드웨어를 연결해 시뮬레이션에서 실제 로봇으로 이어지는 실행 환경을 제공한다.
시뮬레이션용 자산 라이브러리 ‘심레디 센트럴 라이브러리(SimReady Central Library)’에는 로봇과 공장 관련 자산 2000개 이상이 포함된다. 인간의 다양한 활동과 3D 손 추적 정보를 담은 ‘휴먼 1M 데이터셋(Human 1M Dataset)’도 공개됐다.
엔비디아는 DGX 스테이션(DGX Station)용 오픈소스 레퍼런스 워크플로 3종도 선보였다. 이를 통해 개발자는 강화학습으로 GR00T 모델을 개선하고, 정교한 물체 조작 기술을 학습하며, 합성 데이터 생성을 위한 코스모스(Cosmos) 월드 모델을 추가 학습할 수 있다.
엔비디아는 로봇의 산업 현장 배치를 지원하기 위해 엔비디아 IGX 토르(IGX Thor) 기반의 풀스택 안전 플랫폼 할로스도 강화했다. 애자일 로봇과 어질리티(Agility), 덱소리(Dexory), 포트 로보틱스(FORT Robotics), 키온(KION) 등이 자사 안전 체계에 할로스를 통합하고 있다.
유럽 로봇 기업들의 플랫폼 활용도 확대되고 있다. ABB 로보틱스(ABB Robotics)는 엔비디아 옴니버스(Omniverse)를 활용해 로봇 시스템을 가상 환경에서 시뮬레이션하고 사전 검증한다. 쿠카(KUKA)는 공장 시뮬레이션에 실시간 렌더링 기술을 적용하고 있다.
뉴라 로보틱스(NEURA Robotics)는 아이작 심과 아이작 랩으로 합성 학습 데이터를 생성하고 시뮬레이션 환경에서 로봇 기술을 학습시켜 자사 멀티모달 기반 모델 뉴런 AI(Neuron AI)를 개발하고 있다. 토요타 머티리얼 핸들링 유럽(Toyota Material Handling Europe)과 소프트서브(SoftServe)는 엔비디아 기술을 활용한 자율 물류 처리 솔루션으로 배포 시간을 최대 50% 단축할 수 있다고 밝혔다.
엔비디아의 이번 발표는 범용 로봇 개발의 초점이 개별 하드웨어 성능을 넘어 데이터와 학습, 시뮬레이션, 안전을 아우르는 통합 개발 환경으로 확대되고 있음을 보여준다. 로봇이 다양한 작업과 환경에 적응할 수 있도록 개발 전 과정을 연결하는 플랫폼이 산업용 피지컬 AI 확산의 핵심 기반으로 부상하고 있다.

기업용 AI 멀티미디어 제작 플랫폼 팔(fal)은 20일(현지시간) 독일 AI 모델 개발사 블랙 포레스트 랩스(Black Forest Labs)와 공동 개발한 비디오 생성 모델 '플럭스 3 맥스(FLUX 3 Max)'를 출시했다.

사후 학습과 추론 최적화 기술을 적용한 결과물로 소개했다. 기존 '플럭스 3 비디오(FLUX 3 Video)' 모델을 기반으로 영상 품질을 개선하면서 생성 속도도 높였다는 것이다. "플럭스 3의 품질을 50 Elo 포인트 높이는 동시에 영상 생성 속도를 11.5배 개선했다"고 밝혔다.
실사에 가까운 표현과 자연스러운 움직임, 영화 같은 조명, 세밀한 질감 구현을 주요 강점으로 내세웠다. 블랙 포레스트 랩스는 음성 표현과 물리적으로 설득력 있는 동작, 음향 효과, 독창적인 장면 생성 등도 강조했다.
아티피셜 애널리시스 벤치마크 기준 플럭스 3 맥스는 1139 Elo를 기록해 시댄스 2.5와 동등한 수준의 선두권 품질을 기록했다. 다만 미니맥스 'H3'가 1124점으로 뒤를 잇는 등 평가 결과의 불확실성 범위가 겹쳐 선두권 모델 사이의 품질 우열을 명확하게 가리기는 어렵다. 또 해당 평가는 '이미지 기반 생성(Image-to-Video)'에 국한된 선호도 측정인 만큼, 전체 성능이나 텍스트 기반 생성 작업 전반을 단정하기는 이르다.
플럭스 3 맥스는 '텍스트-투-비디오(Text-to-Video)'와 '이미지-투-비디오' 기능을 모두 지원한다. 텍스트 기반 생성은 설명문을 입력해 영상을 만들며, 이미지 기반 생성은 시작 이미지를 활용한다. 이미지 기반 작업에서는 종료 이미지도 지정할 수 있다. 최대 10장의 이미지를 영상의 주요 시점에 배치하는 키프레임(Keyframes) 방식도 제공해 장면 전개를 세밀하게 제어할 수 있다.
생성 가능한 영상 길이는 5~20초이며, 기본 해상도는 720p다. 필요에 따라 1080p로 업스케일링할 수 있고, 가로형·세로형·정사각형 화면 비율도 지원한다. 음성 생성 기능은 사용자가 켜거나 끌 수 있다.
가격 경쟁력도 내세웠다. 출시 후 3주 동안 75% 할인된 가격에 제공한다.
정규 API 요금은 720p 기준 초당 0.17달러, 1080p 기준 초당 0.29달러다. 이를 적용하면 10초 영상 한 편의 생성 비용은 각각 1.70달러와 2.90달러다.

[TITLE] "AI 에이전트, 보안 판 바꾼다"…엔비디아 OpenShell 아키텍처 공개, 위험 행동 밀리초 만에 차단
[LINK] https://www.aitimes.kr/news/articleView.html?idxno=42387
[PUBLISHED] 2026-10-22 10:32 KST
[SOURCE] 인공지능신문
[TOPIC] 에이전트, 보안, 규제
[SCORE] 6
[REASON] 기업 에이전트 실행 권한 통제 구조 제시
[FIELD] AI 에이전트
[BODY]
오픈셸 레퍼런스 아키텍처, 실행·감시·통제 통합…오픈AI·앤트로픽·마이크로소프트·SAP 등 협력
엔비디아(NVIDIA)가 기업용 인공지능(AI) 에이전트의 실행 환경과 보안 통제 체계를 통합한 ‘엔비디아 오픈셸 레퍼런스 아키텍처(NVIDIA OpenShell Reference Architecture)’를 공개했다. AI 에이전트가 기업 시스템과 외부 도구에 접근해 자율적으로 작업하는 환경에서 실행 권한을 관리하고, 이상 행동을 감시하며, 보안 정책 위반을 차단하는 인프라를 제공한다는 구상이다.
엔비디아는 21일(현지시간) 독일 베를린에서 열린 GTC에서 해당 아키텍처를 공개했다. 기업이 AI 에이전트를 개발하고 운영하는 데 필요한 컴퓨팅 인프라와 보안 소프트웨어를 결합해 대규모 에이전트 배포를 지원한다.
이번 아키텍처의 핵심은 AI 모델의 추론, 에이전트의 도구 사용, 보안 정책 집행을 각각 최적화된 컴퓨팅 구성 요소에 배치하는 것이다. 엔비디아는 이를 위해 베라 루빈(Vera Rubin) 인프라, 베라(Vera) CPU, 블루필드-4(BlueField-4) 데이터처리장치(DPU), 오픈소스 보안 런타임 소프트웨어인 오픈셸(OpenShell)을 결합했다.
젠슨 황(Jensen Huang) 엔비디아 창업자 겸 최고경영자(CEO)는 “AI 역량과 안전성은 함께 발전해야 한다”며 “기업이 수십억 개의 AI 에이전트 배포를 준비하는 상황에서 안전과 통제 기능은 컴퓨팅 아키텍처 자체에 내장돼야 한다”고 말했다.
베라 루빈·베라 CPU·블루필드-4로 역할 분담
아키텍처에서 베라 루빈은 AI 모델의 사전 학습과 사후 학습, 추론을 담당한다. 엔비디아는 에이전트 중심 워크로드에서 베라 루빈 NVL72 시스템이 메가와트당 처리량을 기존 대비 30배 높일 수 있다고 설명했다.
베라 CPU는 AI 에이전트의 실행 환경인 하네스(harness)와 도구 사용을 처리한다. 엔비디아는 베라 CPU가 x86 프로세서보다 2배 높은 성능과 향상된 에너지 효율을 제공한다고 밝혔다. 오픈셸은 이 환경에서 에이전트가 허용된 범위 안에서만 작업하도록 보안 경계를 설정한다.
보안 정책 집행은 블루필드-4 DPU와 엔비디아 센트리(NVIDIA Sentry)가 맡는다. 센트리는 엔비디아 도카(DOCA) 소프트웨어를 기반으로 에이전트의 행동을 지속적으로 감시하고, 소프트웨어 경계를 벗어나려는 행위를 하드웨어 수준에서 차단한다.
에이전트가 허용된 범위를 벗어나려 하면 센트리가 해당 에이전트를 격리하고 밀리초 단위로 실행을 중단할 수 있다는 것이 엔비디아의 설명이다. 엔비디아는 블루필드-4와 센트리의 결합으로 에이전트 처리 용량을 최대 20% 높일 수 있다고 덧붙였다.
이는 기존 보안 도구를 통해 사후에 이상 행위를 탐지하는 방식에서 나아가, 에이전트가 작업을 수행하는 동안 정책을 감시하고 위반 행위를 인프라 차원에서 집행하는 구조다. 특히 에이전트가 기업 데이터와 업무 시스템, 외부 도구에 접근하는 과정에서 권한 통제와 실행 격리를 강화하는 데 초점을 맞췄다.
클라우드부터 엣지까지...기업용 AI 생태계 확대
오픈셸 레퍼런스 아키텍처는 데이터센터뿐 아니라 엣지 환경에서도 활용할 수 있도록 설계됐다. 엔비디아 RTX 스파크(RTX Spark), DGX 스파크(DGX Spark), DGX 스테이션(DGX Station) 시스템을 통해 소매, 의료, 제조, 로봇, 소프트웨어 개발, 통신 등 다양한 산업의 에이전트 운영을 지원한다.
운영체제와 컨테이너 환경도 폭넓게 지원한다. 캐노니컬(Canonical), 수세(SUSE), 레드햇(Red Hat)의 리눅스 및 쿠버네티스 환경과 마이크로소프트 윈도우 기반 실행 환경인 마이크로소프트 이그제큐션 컨테이너(Microsoft Execution Containers)를 지원하며, 아마존웹서비스(AWS), 구글 클라우드(Google Cloud), 마이크로소프트 애저(Azure) 등 클라우드 환경에서도 사용할 수 있도록 했다.
AI 모델 공급업체로는 앤트로픽(Anthropic), 코히어(Cohere), 구글(Google), 메타(Meta), 오픈AI(OpenAI), 퍼플렉시티(Perplexity), 리플렉션(Reflection), 스페이스X 슈퍼 인텔리전스(SpaceX Super Intelligence) 등이 협력 대상에 포함됐다. 엔비디아는 이들과 함께 오픈셸 기반 에이전트 배포를 추진하고 있으며, 고도화된 모델 연구를 위한 적용도 협의하고 있다.
사이버보안 분야에서는 크라우드스트라이크(CrowdStrike), 시스코(Cisco), 체크포인트(Check Point), 포티넷(Fortinet), 팔로알토 네트웍스(Palo Alto Networks), 마이크로소프트, 옥타(Okta), 지스케일러(Zscaler) 등이 자사 에이전트 보안 솔루션에 대한 지원을 통합하고 있다. 델 테크놀로지스(Dell Technologies), HPE, 레노버(Lenovo), 슈퍼마이크로(Supermicro) 등 시스템 제조업체와 코어위브(CoreWeave), 오라클 클라우드 인프라스트럭처(Oracle Cloud Infrastructure) 등 클라우드 사업자도 관련 인프라 구축에 참여한다.
기업용 소프트웨어 분야에서는 SAP가 비즈니스 AI 플랫폼의 주울 스튜디오(Joule Studio) 런타임에 오픈셸 아키텍처를 통합하고 있다. 서비스나우(ServiceNow)는 장시간 실행되는 개인용 AI 에이전트 ‘서비스나우 아크(ServiceNow Arc)’를 일반에 공개하면서, 서비스나우의 슈퍼 인텔리전스 컨트롤 타워와 엔비디아 오픈셸을 통해 에이전트의 실행 권한과 정책을 통제하도록 했다. 회사는 AI 패스포트(AI Passport)를 통해 소프트웨어와 하드웨어 전반에서 에이전트 접근 권한을 수초 내에 철회할 수 있다고 밝혔다.
유럽의 BBVA와 산탄데르(Santander) 등 은행들도 오픈셸을 에이전트의 안전성·보안·거버넌스 강화를 위한 체계로 검토하고 있다. 다쏘시스템(Dassault Systèmes), IBM, 지멘스(Siemens), 시놉시스(Synopsys) 등 기업용 소프트웨어 업체도 관련 에이전트 플랫폼 개발에 참여한다.
엔비디아의 이번 발표는 AI 에이전트의 성능 향상뿐 아니라 기업 환경에서 자율 실행을 안전하게 관리할 수 있는 기반을 확보하려는 움직임으로 풀이된다. 에이전트가 복잡한 업무를 직접 수행하는 사례가 늘어날수록 접근 권한과 실행 범위를 명확히 정의하고, 정책 위반을 실시간으로 차단하는 기능이 중요해지기 때문이다.
다만 실제 도입 효과는 기업별 업무 환경과 보안 정책, 기존 시스템과의 통합 수준에 따라 달라질 수 있다. 오픈셸 레퍼런스 아키텍처의 확산 여부는 다양한 모델과 운영체제, 보안 제품을 아우르는 호환성과 함께 실제 운영 환경에서의 통제 효과에 달려 있을 것으로 보인다.
한편, 오픈셸 레퍼런스 아키텍처(다운)는 현재 이용할 수 있다. 상세 기술 문서는 엔비디아 공식 사이트(보기)에서 확인할 수 있다.(아래는 소개 영상)
