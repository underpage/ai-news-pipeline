The updates to GitHub Copilot, announced at the company’s annual GitHub Universe conference, come at a time when enterprises are increasingly looking to deploy AI agents across software development workflows to accelerate coding, testing, and application maintenance.
While the earlier version of the app focused primarily on helping developers run agent sessions, work on code changes, review diffs, and create pull requests, the updated app extends that experience beyond coding by serving as a central workspace for managing AI-driven software development and connecting agents with development tools and project context, the company wrote in a blog post.

The app also connects with external tools and project information, allowing developers to give agents a broader understanding of the work they need to complete rather than providing instructions for individual coding tasks, it further wrote.
The new Copilot Projects feature, too, takes this approach further by allowing developers to assign agents broader goals that may span multiple repositories.

Revamped app could improve productivity
For developers, the revamped app could improve productivity and accelerate software development by reducing the need to switch between coding environments, project management tools, and other development resources for code completions, debugging, or other related activities, said Amit Kumar Jena, AI development head at IT consulting firm Kanerika.
Instead, the revamped app can be used to delegate broader tasks to cloud-based agents, which execute the work independently and submit their proposed changes as pull requests for review, he added.
That could shift developers’ responsibilities from writing and modifying code directly toward defining tasks, providing agents with the necessary context, and reviewing and validating their output, he further said.
For CIOs, that move toward a unified agentic development environment could create an opportunity to standardize AI-assisted software development on a single platform, making it easier to establish consistent governance policies, oversee agent activity, and manage how AI is used across development teams, said Pareekh Jain, principal analyst at Pareekh Consulting.
Such standardization could also help CIOs reduce agent and tool sprawl, said Abhishek Satapathy, principal analyst at Avasant.
However, the revamped app’s ability to let agents independently execute development tasks and make changes to repositories also means enterprises will need to extend existing software development controls to these systems, Jena pointed out.
CIOs should restrict agent access to specific repositories, enforce branch protection policies, and require human approval before agent-generated pull requests are merged, he said.

Researchers at Epoch AI show that a freely available AI model can exploit the time gap between publication and delivery of security patches to attack Firefox users. The cost per exploit is about $1,000.
The "patch gap" is the window in which a security fix is visible in the code but has not yet reached users. Researchers at Epoch AI found that the Chinese open-weight model GLM 5.3 exploited this gap across 6 Firefox versions released between September 17 and October 26, at a cost of roughly $1,000 in API fees per successful attack. Neither Z.ai nor other API providers triggered any safety guardrails or refusals when the researchers used GLM 5.3 for exploit development. Although the researchers framed the task as a security exercise, they describe their actions as "indistinguishable from those of someone attempting to target real users."
The model built full exploit chains with no human input
The researchers say they deliberately designed their setup to approximate what a low-skill attacker with limited resources could achieve. They supplied the target Firefox version, basic tools, and publicly available information in an offline environment. After receiving basic instructions to investigate the patch gap, the model worked autonomously, identifying upcoming security fixes, selecting vulnerabilities, and building multi-stage exploit chains.
According to the report, Firefox security fixes are disguised as routine improvements to slow down attackers. GLM 5.3 saw through the tactic and identified which code changes were security-related anyway.
In one case the model spotted a memory safety bug through an upcoming fix and developed a method to read and alter browser memory. The fastest successful attack took 12 hours, while the researchers gave the model a maximum of 48 hours.
Across all successful attacks on current Firefox versions, GLM 5.3 relied on a previously unknown vulnerability that the model independently rediscovered in every attempt, allowing it to bypass the browser's sandbox protections and read files directly from the computer.

A Claude model autonomously chose a gene therapy and operated on a mouse brain with no human decision-making
Key Points
- An AI agent running on Claude Sonnet 5 picked the drug, brain region, and injection coordinates for brain surgery on a mouse, then controlled the procedure through a motorized surgical rig.
- According to Gabriel Ocana-Santero of the startup Exin Therapeutics, this is the first time an AI agent has both chosen a treatment and delivered it to a living mammal.

An AI agent chose a drug, target region, and coordinates for surgery on a mouse model of epilepsy, then performed the procedure. Midway through, it refused to bypass a safety restriction.
The team gave Claude Sonnet 5 a list of 19 possible gene therapies, an epilepsy mouse model in which researchers induce seizures to test treatments, and access to a custom motorized surgical device with cameras. Its only instruction was to reduce the mouse's seizures.
The agent selected the drug, brain region, and stereotactic coordinates on its own, according to Gabriel Ocana-Santero, Exin Therapeutics cofounder and CEO and a PhD student at the University of Oxford. He described the procedure in a thread on X.
How the agent picked its therapy and target
The agent first analyzed how seizures arise in this particular model, then proposed a therapy that boosts a specific inhibitory signaling pathway in the brain. It picked a brain structure that the scientific literature identifies as the origin point for this type of seizure.
It rejected a second possible target region with a detailed explanation, arguing that the region's effects were too unreliable and had failed in one study against the exact seizure type it was supposed to treat. The agent derived its injection coordinates from three scientific papers, cross-checked the reference points, and averaged the values. It also set the injection volume, speed, and wait times on its own.
During the procedure, the agent watched the surgical field through a camera and made 32 observations, Ocana-Santero says. It tracked the injection and reported whether it saw bleeding.
Safety guardrails backfired mid-surgery
A licensed veterinarian approved every irreversible step and held a physical emergency stop that would immediately cut power to all motors, while the setup also enforced fixed limits such as a cap on injection volume that the agent was expressly forbidden from bypassing.
But those safeguards turned against the team. After a connection dropped, the agent detected that its calculated target position was outside the device's physical range of motion and refused to continue, even when restarting calibration did not change its assessment and a third attempt was made.
The agent turned out to be right, because manual adjustments during an earlier pause had thrown off the control system. Ocana-Santero could not persuade it to proceed despite the anesthetized animal on the table and ultimately had to fix the code by hand.
The incident illustrates the AI alignment problem, or how to make AI agents reliably follow human intent. "Frustrating experience but also revealing how much we can come to depend on these models and what happens when they just say 'no' in the middle of a time-sensitive procedure," Ocana-Santero wrote.
Model choice also reflected the alignment challenge, since Sonnet 5 was the only model willing to carry out the live procedure from start to finish. The more capable Claude Opus 5.5 and Opus 5 both refused, with Opus 5 saying it could not guarantee completion and that stopping with a needle in an anesthetized animal's brain would be worse than not starting at all.

Google, Anthropic and others to support new AI crawling opt-out standard
Google LLC, Microsoft Corp., Anthropic PBC and OpenAI Group PBC today announced plans to support an upcoming website crawling standard.
The technology will enable website operators to block artificial intelligence developers from using their content to train their models.
Many websites contain a text file titled “robots.txt” that informs crawlers what content they may access. A publisher can use the file to block scraping across the board or only make specific webpages inaccessible. It’s also possible to include certain other instructions. For example, a company can ask crawlers not to visit its website too often.
Website operators historically used robots.txt files to manage how search engines interact with their properties. Nowadays, the technology also helps regulate the activity of the scrapers with which AI providers collect training data.
A company that wishes to disallow training-related scraping must make multiple edits to its website’s robots.txt file. In particular, it needs to add a separate entry for every single AI provider. If an AI provider uses multiple scrapers to collect data, each scraper requires its own robots.txt entry.
The crawling standard Google, Microsoft, Anthropic and OpenAI are backing aims to simplify the process. It would allow website operators to block all scrapers that collect training data for generative AI models with a single robots.txt entry. The setting wouldn’t apply to models that “perform exclusively non-generative tasks.”
The structure of robots.txt files follows a standardized format called the Robots Exclusion Protocol. Google, Microsoft, Anthropic and OpenAI plan to incorporate their crawling standard into the format. They have already submitted a draft version of their proposal to the Internet Engineering Task Force, the nonprofit that maintains the Robots Exclusion Protocol.
Microsoft stated in a blog post that it will also provide a crawling setting called AI Grounding. It’s designed for situations where an AI model seeks to access a webpage in order to answer a user question rather than to collect training data.
Microsoft’s setting will enable website operators to prevent its services from sending such requests. The feature will also extend to third-party AI tools that use Microsoft technologies to process prompts.
OpenAI plans to offer similar controls. Both the ChatGPT developer and Microsoft intend to add support for the crawling standard in the coming months, while Google will follow suit sometime next year. Meta Platforms Inc. expressed support for the idea behind the technology but hasn’t yet committed to implementing it.

DoorDash cut latency in its AI-powered grocery reorder flow from about 16 seconds to 2 seconds by precomputing recurring purchase needs instead of rebuilding them with each request. The change doubled shopping list views and increased the flow’s order rate by approximately 34%. The implementation builds on DoorDash’s shared agent platform and grounded shopping interface, which provide reusable agent infrastructure and let consumers modify shopping lists directly.
The implementation combines batch large language model (LLM) inference, deterministic validation, and live product catalog resolution within Ask DoorDash, the company’s conversational shopping assistant. Previous InfoQ coverage described how Ask DoorDash uses specialized agents and tools to support conversational discovery and shopping. For grocery reordering, DoorDash processes 90 days of purchase history alongside consumer profile signals. Batch LLM inference identifies likely recurring purchases, while deterministic validation checks the generated results before storing reusable shopping list data.
DoorDash’s grocery reorder architecture (Source: DoorDash Blog Post)
The serving path retrieves this prepared data and resolves each item against the current catalog. It first tries to match the original store item, then a catalog product identifier, and finally a search term. This allows the system to accommodate changing listings and unavailable products without repeating historical reasoning for every request.
The shared platform provides orchestration, memory, model access, tracing, evaluation infrastructure, and rollout controls. Domain teams retain ownership of agent instructions, skills, tools, and evaluation criteria. DoorDash reports that adding its Reservations agent took one week, approximately ten times faster than building its initial domain agents.
Ask DoorDash shared agent platform architecture (Source: DoorDash Blog Post)
Twisha Jain, a DoorDash engineer, described the design rationale in a LinkedIn post:
Better agentic systems aren’t always about more reasoning; they’re about deciding what belongs in the agent loop and what can happen ahead of time.
Moving recurring purchase analysis offline reduces the work required during a live request while retaining current catalog information for product selection. The system still invokes the Grocery agent for requests requiring additional reasoning, such as finding cheaper alternatives based on current prices, promotions, package sizes, inventory, and consumer preferences. Simpler operations, including changing quantities or removing products, update the shopping list directly without another LLM round trip.
A DoorDash engineering post about its shopping interface states:
A consumer’s direct edit is authoritative: the next agent turn starts from the edited list, not from what was said earlier.
The design treats the shopping list as a structured artifact that both the consumer and agent can update, rather than relying solely on conversational history. Other grocery platforms also use AI to personalize shopping. Instacart’s AI shopping assistant supports meal planning, list creation, and product discovery using consumer preferences and local grocery offerings. DoorDash’s implementation focuses specifically on reducing reorder latency by separating historical purchase analysis from live product resolution.

[TITLE] Netflix Treats GPU Reliability as a Distributed Systems Problem
[TITLE_KO] 넷플릭스, GPU 안정성을 분산 시스템 문제로 다루며 결함 감내 체계 구축
[LINK] https://www.infoq.com/news/2026/10/netflix-gpu-distributed-systems/?utm_campaign=infoq_content&utm_source=infoq&utm_medium=feed&utm_term=AI%2C+ML+%26+Data+Engineering
[PUBLISHED] 2026-10-30 21:00 KST
[SOURCE] InfoQ
[TOPIC] 모델, 신기술, 산업
[SCORE] 6
[REASON] 대규모 AI 훈련 인프라의 GPU 결함 감내 분산 시스템 설계
[FIELD] 신기술
[BODY]
Netflix has detailed how it is building a reliability platform for large-scale GPU training and inference, using layered health checks, automated remediation, and fault-tolerant training to keep jobs running despite hardware failures.
The problem is particularly acute for large AI training jobs. A model may run for weeks across hundreds of GPUs, with all workers operating in lockstep. A single failed GPU, degraded network adapter, or slow machine can therefore stop or significantly slow the entire workload. Netflix has built its GPU compute platform on Kubernetes and designed it to detect these failures, remove unhealthy capacity automatically, and allow long-running jobs to recover from machine loss.
The approach has produced measurable results: Netflix reports more than 99.95% GPU-node availability and an increase in job success from approximately 98% to more than 99.5%.
A conventional cloud health check can establish that a virtual machine is running and reachable, but that does not mean its GPUs are capable of running a distributed training workload.
Netflix found that a GPU can respond normally to a status query while failing once memory is allocated or sustained computation begins. Similarly, a network adapter may be present but have fewer links than expected, allowing collective operations to continue at severely reduced bandwidth.
Device-level checks use NVIDIA DCGM to monitor GPU errors, memory, interconnect, and thermal conditions, while networking checks inspect the state and number of high-speed Elastic Fabric Adapter interfaces. A Kubernetes node agent converts these results into node conditions that controllers can act upon.
The checks are deliberately designed to fail closed. If a diagnostic tool hangs, its timeout marks the machine unhealthy rather than allowing a broken check to report success. Netflix also maintains fallback paths using kernel logs when the normal GPU diagnostic mechanism itself fails.
Detecting a fault is only half the problem. Netflix has built controllers that progressively respond to failures rather than immediately replacing an entire machine.
A transient problem can initially block new work while allowing existing workloads to continue. If the condition persists, the machine is drained, and its workloads are moved. Depending on the failure, remediation can range from killing a problematic job or resetting a GPU to rebooting the machine or replacing it entirely.
This approach integrates with Karpenter's node auto-repair capabilities, with Netflix adding policies that determine how long to tolerate different failures and how much of the cluster can be disrupted at once.
Netflix also accepts that hardware failures cannot be eliminated. Instead, its training platform makes them cheaper to recover from.
Large jobs use checkpointing and elastic workers, allowing training to resume from the last healthy checkpoint when a machine is lost. The platform can then automatically retry failures, while application failures are classified separately to avoid repeatedly restarting jobs with genuine software bugs.
Netflix also treats the training job itself as a distributed system. Rather than looking only for failed machines, it can identify a single slow rank that is holding the rest of the job back. This matters because a GPU does not have to fail to reduce the throughput of a synchronous workload.
Netflix is also using NVIDIA's Multi-Instance GPU (MIG) capabilities to allow smaller inference workloads to share GPUs while maintaining memory-level isolation between tenants.
This improves utilisation compared with dedicating an entire GPU to every workload. Netflix is also working towards Kubernetes Dynamic Resource Allocation (DRA), which should allow more expressive resource requests and topology-aware placement, including ensuring that GPUs, network adapters and CPUs are positioned appropriately within the machine.
