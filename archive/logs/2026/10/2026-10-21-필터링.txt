[TITLE] “모델 가중치 그대로 두고 ‘AI 에이전트’ 스스로 진화시킨다”...구글, ‘하네스²’ 오픈소스로 공개
[LINK] https://www.aitimes.kr/news/articleView.html?idxno=42369
[PUBLISHED] 2026-10-20 22:48 KST
[SOURCE] 인공지능신문
[TOPIC] 에이전트, 개발, 모델
[SCORE] 8
[REASON] 에이전트 개발자는 실행 환경 자동 개선 활용
[FIELD] AI 에이전트
[BODY]
프롬프트·도구·메모리 등 실행 환경을 스스로 개선…모델 재학습 없이 성능 최적화, 정답 레이블 없는 오픈월드서 이중 재귀 적용
구글 리서치(Google Research)가 대형언어모델(LLM)의 가중치를 변경하지 않고도 인공지능(AI) 에이전트의 실행 환경을 반복적으로 개선하는 오픈소스 프레임워크 ‘하네스²(Harness²·Harness Squared)’를 공개했다.
모델 자체를 재학습하는 대신 프롬프트, 도구 사용법, 메모리, 작업 절차 등 주변 구성 요소를 진화시켜 에이전트의 실제 수행 능력을 높이는 접근법이다. 이 프레임워크는 AI 성능 향상의 초점을 모델 내부에서 외부 실행 체계로 확장한다는 점에서 주목된다.
에이전트가 복잡한 업무를 수행할 때는 모델의 추론 능력뿐 아니라 작업 계획, 도구 선택, 오류 복구, 과거 경험의 활용 방식도 결과에 영향을 미친다. 하네스²는 이러한 실행 환경을 고정된 설정값이 아니라 지속적으로 개선할 수 있는 대상으로 다룬다. 특히 사전에 정답이나 평가 사례가 마련되지 않은 새로운 과제에서도 에이전트의 행동을 비교해 개선점을 찾고, 그 경험을 다음 과제에 활용하도록 설계됐다.
모델이 아니라 실행 환경을 개선한다
하네스²는 모델의 가중치를 고정한 채 시스템 프롬프트와 행동 지침, 메모리, 도구 사용 가이드, 서브에이전트, 스킬, 스크립트, 플러그인 등 8개 구성 요소를 수정 대상으로 삼는다. 이 요소들은 모델에 어떤 정보를 제공하고, 어떤 도구를 호출하며, 여러 작업을 어떻게 분배하고, 실패했을 때 어떤 행동을 취할지를 결정한다.
예를 들어 AI 에이전트가 계약서를 검토하면서 관련 조항을 놓친다면 더 강력한 모델로 교체하는 대신 검토 순서나 검색 도구 활용 지침, 메모리 구조를 개선할 수 있다. 하네스²는 이처럼 모델이 이미 가진 능력을 실행 환경이 충분히 끌어내지 못하는 문제를 해결하는 데 초점을 맞춘다.
이는 프롬프트의 표현을 다듬는 수준을 넘어 도구 연결, 작업 분배, 실행 절차까지 개선 대상으로 삼는다는 점에서 차별화된다. 모델 자체의 지식과 추론 능력을 확장하는 방식과 달리, 기존 모델의 능력을 실제 업무에 맞게 활용하는 방법을 최적화하는 것이다.
정답 없이 개선점을 찾는 이중 재귀
하네스²의 핵심은 이중 재귀(Dual-level Recursion) 구조다. 첫 번째는 개별 과제의 수행 방식을 개선하는 과제 수준 재귀(Task-level Recursion)이며, 두 번째는 개선 과정에서 얻은 경험을 축적해 향후 과제에 활용하는 하네스 수준 재귀(Harnessing-level Recursion)다.
과제 수준 재귀는 제안(Propose), 탐색(Probe), 구성(Compose)의 세 단계로 진행된다. 먼저 기존 실행에서 드러난 문제를 해결할 하네스 변경안을 제안하고, 변경된 설정으로 과제를 수행해 행동과 결과를 비교한다. 이후 실행 증거를 바탕으로 효과적인 변경 사항을 조합해 개선된 하네스를 구성한다. 이 과정을 반복하면서 계획 수립이나 도구 활용, 정보 처리 방식 등을 정교화한다.
이 과정에서 중요한 것은 정답 레이블 대신 행동적 대비(Behavioral Contrasts)를 활용한다는 점이다. 동일한 과제에서 설정을 달리했을 때 에이전트의 행동과 결과가 어떻게 달라지는지를 관찰해 개선의 근거를 확보한다. 사전에 정답이 준비되지 않은 오픈월드 환경에서도 실행 결과의 차이를 통해 개선 가능성을 탐색할 수 있다는 것이다.
다만 행동의 차이가 곧바로 업무 품질의 향상을 의미하지는 않는다. 실제 적용에서는 최종 결과물의 정확성, 완전성, 과제 성공 여부 등을 별도로 검증해야 한다.
한 번의 개선을 다음 과제의 자산으로
하네스 수준 재귀는 개별 과제에서 확보한 개선 경험을 지속적으로 축적하고 재사용하는 과정이다. 예를 들어 경쟁사 분석을 수행하는 에이전트가 검색 결과를 충분히 검증하지 않는 문제를 반복한다면, 과제 수준 재귀를 통해 조사 지침과 검색 전략을 개선할 수 있다. 이후 효과가 확인된 절차와 경험을 저장하면 다음 시장 조사 과제에서 이를 활용해 개선을 이어갈 수 있다.
이 구조는 에이전트가 매번 동일한 시행착오를 반복하지 않고, 과거의 개선 경험을 다음 실행의 출발점으로 삼도록 한다. 공개 자료에서 언급하는 EXPERIENCE.md와 같은 기록도 이러한 경험 축적 구조를 보여주는 사례다.
그러나 이를 모델 자체가 오류를 통해 학습하는 것과 혼동해서는 안 된다. 하네스²는 모델 가중치를 변경하지 않으며, 축적된 경험이 자동으로 모델 내부의 지식으로 편입되는 것도 아니다. 경험은 외부에 저장돼 향후 실행 환경을 개선하는 데 활용된다. 즉, 모델의 자기 학습보다는 에이전트 시스템의 지속적인 자기 개선에 가까운 접근이다.
전문 업무 벤치마크에서 성능 개선 확인
구글 리서치의 공개 자료에 따르면 하네스²는 세 가지 전문 업무 벤치마크와 네 가지 모델·하네스 구성 조합에서 개선 효과를 보였다. 사무·웹·코딩 업무를 평가하는 워크버디 벤치(WorkBuddy-Bench)에서는 최대 11.5점, 전문 직무 수행을 평가하는 잡벤치(JobBench)에서는 최대 4.5점의 향상이 보고됐다. 법률 관련 업무를 다루는 랩(LAB)에서는 부분 통과율이 최대 11.8%포인트 상승했다.
연구진은 GLM-5와 제미나이 3.5 플래시(Gemini 3.5 Flash)를 포함한 모델·하네스 구성에서 기본 하네스보다 나은 결과를 확인했으며, 개선 반복 예산을 늘리면 추가적인 성능 향상도 가능하다고 설명했다.
이 결과는 동일한 모델을 사용하더라도 실행 환경을 어떻게 구성하느냐에 따라 업무 수행 결과가 달라질 수 있음을 보여준다. 다만 제시된 수치는 벤치마크별 최대 개선 폭이며, 모든 과제와 모델에서 같은 수준의 향상이 보장되는 것은 아니다. 벤치마크 성능이 실제 기업의 생산성 향상으로 그대로 이어진다고 단정하기도 어렵다.
또한 모델 가중치를 바꾸지 않더라도 개선 과정에서 모델 호출과 도구 실행 비용이 발생한다. 따라서 실무 도입 시에는 성능 향상뿐 아니라 반복 실행에 필요한 비용과 시간까지 함께 평가해야 한다.
오픈소스 공개와 실무 적용의 과제
하네스²는 구글 리서치의 공개 저장소(다운)에서 확인할 수 있으며, 아파치 2.0(Apache 2.0) 라이선스로 배포된다. 공개 구현은 파이썬 3.12 이상 3.14 미만 환경을 요구하며, 실행기로 오픈코드(OpenCode)와 코덱스(Codex)를 지원한다. 병렬 재귀를 활용해 여러 하네스 후보를 동시에 탐색하거나, 순차 재귀를 통해 앞선 개선 결과를 바탕으로 단계적으로 최적화할 수 있다.
다만 현재 공개 구현은 지원되는 벤치마크와 실행 환경을 중심으로 구성돼 있어 모든 기업 업무에 별도 설정 없이 즉시 적용할 수 있는 완성형 범용 제품으로 보기는 어렵다. 실제 환경에서는 모델 인증과 의존성 설정이 필요할 수 있으며, 개선된 설정이 기존 업무의 품질이나 보안을 저해하지 않는지도 검증해야 한다.
특히 특정 과제에서 효과가 있었던 지침이 다른 분야에서도 유효하다는 보장은 없다. 도구와 스크립트의 변경은 시스템 접근 권한과 실행 행동에도 영향을 줄 수 있으므로 변경 이력 관리, 회귀 테스트, 권한 통제 등을 함께 갖춰야 한다. 자율적인 개선 범위를 넓히더라도 실제 운영 환경에서 허용되는 행동은 별도로 통제할 필요가 있다.
AI 경쟁의 초점, 모델에서 에이전트 시스템으로
하네스²는 AI 성능 향상의 기준이 모델의 규모와 추론 능력에만 머물지 않을 가능성을 보여준다. 모델이 강력하더라도 실행 환경이 비효율적이면 능력을 충분히 발휘하기 어렵다. 반대로 적절한 도구와 메모리, 작업 절차를 갖추면 동일한 모델로도 더 나은 결과를 얻을 수 있다.
물론 하네스 최적화가 모델 업그레이드나 미세조정을 대체하는 것은 아니다. 모델 자체의 지식이나 추론 능력이 부족한 문제는 주변 환경을 개선하는 것만으로 해결되지 않을 수 있다. 두 접근법은 서로 다른 병목을 해결하는 보완적인 수단이다.
하네스²의 의미는 모델을 더 크게 만드는 것뿐 아니라, 이미 확보한 능력을 실제 업무에 맞게 활용하고 실행 경험을 축적하는 방식도 AI 발전의 중요한 축이 될 수 있음을 보여준다는 데 있다.

Update 10/21/26: The PHP Foundation's emergency patches have been released, and you can learn more in our new article on PHP2Shell and the updates.
The PHP security team is warning administrators to prepare for emergency security updates tomorrow to address two critical vulnerabilities, as information about the flaws has reportedly leaked ahead of their scheduled disclosure.
PHP powers many websites and web applications, including content management systems, e-commerce platforms, and custom web services.
In an advisory published Tuesday, the PHP development team announced that it plans to release security updates on Wednesday, October 21, at 14:00 UTC (10:00 AM Eastern), to address two vulnerabilities, each rated 9.2 under CVSS v4.0.
The PHP security team also sent a notice to its ANNOUNCE mailing list, urging administrators to prepare to install the security updates as soon as they become available.
"We reserve the right to release earlier should details of either vulnerability become public, or should evidence of active exploitation appear in the wild," the PHP security team warned.
The developers have not disclosed any technical details about the vulnerabilities, including which PHP versions are affected, how they can be exploited, or which releases will contain fixes.
However, security researchers at watchTowr told BleepingComputer that the vulnerabilities, tracked as CVE-2026-109618 and CVE-2026-109619, are remote code execution (RCE) flaws believed to affect PHP versions 5, 6, 7, and 8.
"In the last hour, two remote code execution vulnerabilities in PHP have been leaked. These vulnerabilities were previously scheduled under embargo and due for release on Thursday at 11 am ET," watchTowr CEO Benjamin Harris told BleepingComputer.
"While we are not able to share technical information at this point for obvious reasons, given the sensitivity, we can confirm that these vulnerabilities are indeed real. Both of them are CVSS10 and are understood to affect PHP versions 5, 6, 7, and 8."
watchTowr also said it believes it has successfully reproduced CVE-2026-109618 but is not releasing technical information until security patches become available.
The researchers clarified that they have not observed exploitation of the vulnerabilities in the wild, despite the information reportedly leaking ahead of the planned disclosure.
In a post on X, watchTowr warned that information about the vulnerabilities had leaked before the originally planned disclosure date.
"We were all supposed to wait until Thursday at 11am ET. Information has leaked wrt zero-day embargoed RCE vulns in PHP. We can confirm that they're real," the researchers said.
The warning follows a now-deleted post on Y Combinator's Hacker News forum, in which a user named "petecooper" claimed that two critical PHP remote code execution vulnerabilities would be disclosed on October 22.
The post, seen by BleepingComputer, claimed that both vulnerabilities carried CVSS scores of 10.0 and affected PHP versions dating back to PHP 5.
It also identified the vulnerabilities as CVE-2026-109618 and CVE-2026-109619, matching the identifiers watchTowr later shared.
However, watchTowr's statements and the Hacker News post are different from PHP's official announcement. Both described the vulnerabilities as CVSS 10.0, while the PHP security team assigned each a CVSS v4.0 score of 9.2.
Additionally, watchTowr cited an originally planned Thursday disclosure, while PHP has officially scheduled its security release for tomorrow morning.
The PHP security team says it will publish full technical details, affected versions, and fixed releases when the security updates become available.
Update October 21: Cloudflare has released an emergency update to its managed Web Application Firewall (WAF) ruleset to help protect customers against the upcoming PHP vulnerabilities, which researchers have begun referring to as "PHP2SHELL."

기존 PyTorch 모델을 TPU에서 실행
- TorchTPU는 Google Cloud TPU에서 PyTorch 모델과 연산을 실행하는 네이티브 백엔드
  - Google과 Meta의 PyTorch 팀이 협력해 개발
  - 기존 모델의 코드 변경을 최소화하면서 학습과 추론을 TPU로 이전하는 것이 목표

DeepSeek open-sources DeepInfer, the inference framework behind its production services
Chinese artificial intelligence startup Hangzhou DeepSeek Artificial Intelligence Basic Technology Research Co. Ltd. today open-sourced DeepInfer, the inference framework behind its own production services.
The release takes on the cost of serving large models to the public. DeepSeek calls reaching a massive user base at a reasonable price “the core problem an inference framework has to solve” in a deployment Q&A posted with the code. One cluster now serves 155 trillion tokens a day, according to the same document, and revenue at off-peak pricing works out to $38 per graphics processing unit per hour.
For now DeepInfer supports a single model, DeepSeek-V4.1-Flash, and by default it loads the updated 1017 version DeepSeek released over the weekend. Nvidia Corp.’s SM100 Blackwell GPUs can run the framework, as can Ascend 950 neural processing units from Huawei Technologies Co. Ltd. Hopper and other older Nvidia architectures are not on the list.
Two features that keep outputs identical from run to run work only on Nvidia hardware. All of the published performance benchmarks ran on Nvidia chips too, and the figures are DeepSeek’s own.
Speculative decoding in DeepInfer runs through DSpark, a system in which a draft model proposes five tokens at a time and a confidence head predicts which of them the main model will accept. Verification compute goes only to the likeliest candidates. That trims the number of draft tokens checked per step by about 30%, and DeepSeek estimated a 4% to 7% throughput gain at its production load. A second technique, which the company says nearly halves total prefill computation, runs only the last 128 tokens of each prompt back through the model’s decoder layers.
DeepSeek has not yet released its key-value cache management and load-balancing code, saying the two are tightly coupled to internal infrastructure. A blog post the company published on Zhihu lays out how both work. Splitting prefill and decode across separate machines is also left to operators, with the README noting that most of the engine work for it is already in place. The smallest deployment DeepSeek describes as efficient uses 64 GPUs for prefill and another 64 for decoding.
The same coupling kept DeepSeek from releasing its full engine in April 2025, when it described the software as an early fork of vLLM built around its cluster management tools. Maintaining a large open-source project was also more than “a small research team focused on developing better models” had bandwidth for, the company wrote at the time.
DeepSeek had already released components such as the FlashMLA, DeepGEMM and DeepEP kernel libraries, which DeepInfer now uses. The new README names vLLM as its original foundation.

Effective and efficient use of complex agentic systems is important for all organizations, but recognizing, preventing and recovering from them going rogue could be an existential necessity.
NIST, the NSA, and CISA recognize the increasing potential for AI agents to behave in an unexpected and potentially harmful manner, and has responded with a list of key practices for both preparing for and responding to such behavior. The report (Key Practices for Incident Readiness and Response in Super Intelligence Training and Evaluation) uses the term super intelligence (SI) rather than artificial intelligence (AI) in line with presidential executive order 14434.
In the report, the ten key practices are grouped into five stages: prepare, detect, respond, recover, and report. For clarity, the report also includes three useful terminology definitions covering AI agents, AI control incident, and AI control near-miss.
“The practices are intended to help the frontier SI industry prevent, prepare for, and respond rapidly to incidents in which SI systems do not act as intended or authorized,” the agencies explain.
Preparation includes activities such as asset and risk inventories, defense-in-depth, least privilege, zero-trust controls, credential management, supply chain risk management and more.
Detection requires continuous monitoring for correct behavior, and anomalous activity and indications of compromise.
Response entails isolating affected systems, revoking credentials, rebuilding compromised environments, determining the blast radius, and conducting root-cause analysis that looks past the specific vulnerability exploited.
Recovery requires testing restoration procedures in advance and documenting recovery decisions along with any residual risk accepted.
Reporting requirements are three-fold: report incidents to all affected parties, wherever required by law, and publicly and widely.
None of the stages or practices is given any greater weight over the others. Instead, the five stages should be treated as a single target. Complex agents all have the potential for misbehavior bordering on rogue and dangerous. These ten practices combine to help organizations develop a stable and effective environment for complex agentic systems, where problems can be detected early and effective operation maintained.
Only the final two practices (#9 and #10 in the Report stage) go beyond the more technical steps of incident readiness and response.
The first of these, ‘Notify Government’, may be a legal requirement, including: “Adhere to any applicable legal reporting requirements, including cybersecurity incident reporting obligations to CISA, law enforcement, and/or cyber-defense organizations.”
The last, Share Information Publicly, is mainstream good behavior throughout cybersecurity that will benefit everyone: “Share details with the public, where appropriate, as early as feasible,” and “Identify and publicly report key practices, takeaways, or improvements adopted in response to the incident or that could benefit other actors in the ecosystem.”
The value of this document is not in providing any new or unrecognized information for AI agent governance, but in providing a very clear and thorough checklist for use by security professionals to maximize the use of agents while minimizing or recovering from agentic incidents.

“We are not forking TypeScript”: Cloudflare spearheads Rust port written by agents, for agents
Cloudflare is going all-out to ensure that AI coding agents can check their work without exhausting available computing resources, leading a new effort to bring Microsoft’s TypeScript compiler to Rust.
But whatever you do, don’t call it a fork.
Taking to X, Cloudflare’s director of engineering Christoph Nakazawa confirmed that the company is taking ownership of tsrs, a Rust port of TypeScript that it claims is up to eight times faster, and uses 70% less memory than TypeScript 7.0.
Microsoft’s own TypeScript compiler is reaping the benefits, too, with the teams sharing optimizations as they work to keep the two implementations in sync.
“We are not forking TypeScript — we are working with the TypeScript team and as a result 7.1 is already ~2.5x faster, too,” Nakazawa writes.
That “port vs fork” message runs throughout the accompanying blog post, co-authored by Nakazawa and fellow Cloudflare engineers Boshen Chen and Dimitri Mitropoulos, who go to great lengths to explain that they very much see TypeScript as Microsoft’s to continue steering.
“To be clear, we are not forking TypeScript. We believe the TypeScript team should remain in full control of the language’s design and direction.”
“To be clear, we are not forking TypeScript,” they write. “We believe the TypeScript team should remain in full control of the language’s design and direction. They have maintained a long-term vision while guiding TypeScript’s adoption across the JavaScript community. We do not want to change that.”
Why Rust, when Microsoft already has Go?
Developed and released by Microsoft back in 2012, TypeScript extends JavaScript with a type system that helps developers catch errors before their applications run. However, checking those types can consume considerable computing resources, particularly in large projects where multiple AI agents may be writing and validating code simultaneously.
Microsoft addressed some of those performance problems in July with TypeScript 7.0, replacing its JavaScript-based compiler with one written in Go and delivering roughly tenfold speed improvements.
As The New Stack previously reported, Microsoft had considered Rust for the rewrite, but concluded that reproducing TypeScript’s existing architecture in Rust would introduce significant complications around memory management and compatibility.
The performance gains reported for tsrs make for an interesting comparison with Microsoft’s own Go implementation. Commenting in a Hacker News discussion about the Rust port, Daniel Rosenwasser, Microsoft’s principal product manager for TypeScript, notes that “a lot of the speed does not just come down to language choice,” adding that “some of what is going to make TS 7.1 faster and leaner… actually comes from optimizations discovered in tsrs.”
“Some of what is going to make TS 7.1 faster and leaner… actually comes from optimizations discovered in tsrs.”
Separately, Rosenwasser announced TypeScript 7.1 beta earlier today, detailing substantial speed and memory optimizations.
Cloudflare, for its part, sees advantages in Rust that extend beyond compiler performance, particularly its suitability for WebAssembly (Wasm), which allows compiled code to run in browsers and other supported environments. Go can also compile to Wasm, but it has to bring its garbage collector along. Rust gives developers more direct control over memory, making it attractive for resource-constrained environments such as Cloudflare Workers, where AI agents can write, check and build applications inside isolated sandboxes.
And even as Microsoft’s Go compiler gets faster, Nakazawa maintains that Rust offers lasting advantages, including closer integration with the wider ecosystem of Rust-based JavaScript tools, such as Oxlint, a linter that can use TypeScript’s type information to detect potential problems.
