[BODY]
LiteLLM on Friday revealed that an Agent Platform master key accidentally published to a public GitHub repository in late May 2026 ultimately allowed the threat actor to push a malicious version of the popular Python package.
"On May 27, 2026, a configuration file was committed to the public LiteLLM-Labs/lite-harness repository which inadvertently contained the master key to a deployment of the LiteLLM Agent Platform, an open source tool we use for orchestrating agents," LiteLLM's Oliver Jensen and Mateo Wang said.
"The error was quickly identified, the commit force-pushed over, and we identified the exposed keys as requiring revocation. However, key revocation did not occur for the master key."
LiteLLM said the unknown attacker (operating from "69.48.229[.]143") used this unrevoked key on October 10, 2026, to gain access to the Agent Platform and extracted a GitHub CLI OAuth token the service was configured with to allow self-hosted cloud agents to file pull requests to GitHub repositories.
The token, per the developers of the open-source large language model (LLM) gateway, was "not scoped down" and associated with its GitHub organization owner's account.
Gaining access to the token allowed the attacker to possess owner-level access to all repositories across the organization and perform additional credential exfiltration. The sequence of actions performed by the threat actor following this step is as follows -
- October 10, 2026, between 10:11 and 10:12 p.m. UTC: Author commits into throwaway branches on internal repositories to run workflows (BerriAI/litellm and BerriAI/litellm-auto) designed to acquire GitHub CLI Oauth tokens associated with two engineers with maintainer privileges via an attacker-controlled webhook[.]site endpoint. The two runs are deleted minutes later.
- October 21, 2026, between 10:08 and 11:08 a.m. UTC: Override branch protection and alter the release pipeline with the source set to the lookalike repository "Berri-AI/litellm" rather than "BerriAI/litellm."
- October 21, 2026, between 11:39 and 11:40 a.m. UTC: LiteLLM version 1.107.0 gets published to PyPI.
- October 21, 2026, 11:46 a.m. UTC: Docker Hub and GHCR images are published.
- October 21, 2026, between 11:53 and 11:54 a.m. UTC: Production and staging run records are deleted.
- October 21, 2026, 12:06 p.m. UTC: Upwind researcher Lidor Machluf reports the supply chain attack.
- October 21, 2026, 1:23 p.m. UTC: PyPI quarantines LiteLLM version 1.107.0.
- October 21, 2025, 2:20 p.m. UTC: Docker Hub tags v1.107.0, latest, main-latest, and main-stable are removed or repointed to verified clean images.
"In typical operation, building and publishing a release requires being kicked off by an authorized engineer and being approved by a special account locked to a physical device in our office," LiteLLM said.
"This restriction was relaxed earlier this week to accommodate the temporary push for more frequent releases and bugfix backports, allowing any two engineers to trigger and approve a release. As such, the threat actor used one of the tokens to trigger the release (after having repointed the deployer to their malicious repository), and another to approve it."
In addition, the project maintainers noted that the threat actor could have very well loosened this restriction (or removed it entirely) themselves given that they were already in possession of a token belonging to an organization owner. It's suspected that this was not done to evade detection.
LiteLLM also said the workflows are designed to identify and exfiltrate additional keys and tokens, specifically focusing on upstream inference API tokens. In response to the incident, the company said it's working to revoke each and every token associated with every internal system and vendor platform.
The findings rule out LiteLLM's initial hypothesis that the GitHub CLI OAuth tokens were stolen from the logs of an internal LiteLLM deployment.

[TITLE] 구글, 터미널서 AI 에이전트 다루는 '제미나이 API CLI' 오픈소스 공개
[LINK] https://www.aitimes.com/news/articleView.html?idxno=216607
[PUBLISHED] 2026-10-24 16:18 KST
[SOURCE] AI타임스
[TOPIC] 에이전트, 개발
[SCORE] 7
[REASON] 에이전트가 명령줄로 제미나이 기능 호출
[FIELD] AI 에이전트
[BODY]
구글이 터미널에서 제미나이 API의 주요 기능을 사용할 수 있는 명령줄 도구(CLI) '제미나이 API CLI(Gemini API CLI)'를 공개했다. AI 에이전트가 간단한 명령어만으로 이미지와 영상, 음악을 생성하고 문서 분석과 음성 전사까지 수행할 수 있도록 지원한다.
구글은 23일(현지시간) 제미나이 API CLI의 실험적 프리뷰 버전을 공개했다고 밝혔다. 이 도구는 별도의 의존성 설치 없이 실행할 수 있는 바이너리 형태로 제공되며, 맥OS와 리눅스, 윈도우에서 사용할 수 있다. 소스 코드로 직접 설치하는 방식도 지원한다.
이번 도구는 AI 에이전트의 API 활용 과정을 간소화하는 데 초점을 맞췄다. 기존에는 에이전트가 모델 식별자를 직접 찾아야 했고, 일회성 SDK 스크립트를 작성하거나 복잡한 ‘curl’ 명령어를 반복해서 사용해야 했다. 생성된 미디어 데이터를 불필요하게 긴 문자열 형태로 처리하는 문제도 있었다.
구글은 실제 서비스 환경과 터미널에서 작동하는 AI 에이전트의 요구사항이 다르다고 설명했다. 운영 서비스에는 자료형이 명확하게 정의된 클라이언트 라이브러리가 적합하지만, 터미널에서 작업하는 개발자와 자율적으로 명령을 실행하는 에이전트에는 상태를 유지하지 않으면서도 명령어와 입력 형식을 쉽게 파악할 수 있는 CLI가 필요하다는 것이다. 이에 따라 입력과 출력 형식을 예측할 수 있는 인터페이스를 제공해 모델 호출과 결과 처리 과정을 단순화했다.
구글의 AI 개발 도구 생태계는 크게 세 계층으로 구성된다. 첫 번째는 추론과 멀티모달 분석, 미디어 생성, 에이전트 실행을 담당하는 제미나이 API다. 두 번째는 파이썬과 타입스크립트, Go, 자바를 지원하는 구글 제너레이티브 AI SDK로, 실제 서비스와 백엔드 개발에 활용된다. 세 번째인 제미나이 API CLI는 개발자와 셸 기반 AI 에이전트가 터미널에서 API에 직접 접근하도록 지원한다.
제미나이 API CLI는 이러한 과정을 명령어 중심으로 통합했다. 개발자와 AI 에이전트는 터미널에서 모델을 탐색하고 프롬프트를 테스트하는 것은 물론, 이미지·영상·음악 생성과 멀티모달 분석, 음성 전사 등을 실행할 수 있다.
미디어 생성 기능은 구글의 다양한 AI 모델과 연동된다. 이미지 생성에는 '나노 바나나 2.1', 영상 생성에는 '제미나이 옴니 1.1 플래시', 음악 생성에는 '리리아 3.5' 등을 활용할 수 있다. 음성 합성에는 '제미나이 3.8 플래시 TTS'가 포함된다.
음성 합성 기능을 이용하면 여러 화자가 대화하는 음성을 만들 수 있으며, 리아를 통해 배경음악용 연주곡도 생성할 수 있다. 이미지와 영상 생성 결과는 파일로 저장되고, 명령어 출력에는 해당 파일의 경로가 표시된다. 이에 따라 후속 작업에서 생성된 결과물을 별도의 변환 과정 없이 활용할 수 있다.
문서와 미디어 분석 기능도 제공한다. 사용자는 PDF와 이미지, 오디오 파일을 입력해 내용을 요약하거나 음성을 텍스트로 변환할 수 있다. 오디오 전사 결과는 타임스탬프가 포함된 SRT 자막 파일로도 생성할 수 있다. 유튜브 영상 분석도 지원한다.

Our CLI gives your agent power to generate images, videos, text-to-speech, or music, analyze media, transcribe audio, or manage agents.
No more guessing model strings, throwaway scripts or endless curl.
— Dmitry Lyalin (@LyalinDotCom) October 22, 2026
제미나이 API CLI는 구글의 자체 개발 환경에만 국한되지 않는다. 셸 명령어를 실행할 수 있는 AI 에이전트라면 활용할 수 있으며, 구글은 클로드 코드, 코덱스, 오픈클로, 헤르메스, 커서 등을 지원 사례로 제시했다.
구글의 AI 개발 환경인 '안티그래비티(Antigravity)'에서도 현재 이 도구를 사용할 수 있다. 사용자가 에이전트에 이미지나 영상, 오디오 생성 또는 문서 분석을 요청하면, 에이전트가 CLI를 호출해 작업을 수행하고 결과 파일이나 작업 식별자를 후속 단계에 전달하는 방식이다. 안티그래비티와의 네이티브 통합은 추후 지원할 예정이다.
여러 단계에 걸친 조사나 코딩 작업은 백그라운드에서 실행되는 '매니지드 에이전트(Managed Agents)'에 맡길 수 있다. 딥 리서치(Deep Research)와 같은 에이전트에 작업을 위임한 뒤 상호작용 식별자를 이용해 진행 상황을 확인하고 구조화된 결과를 받을 수 있다.
안정적인 자동화 작업을 위한 기능도 갖췄다. 모든 명령어와 옵션을 오프라인에서 확인할 수 있고, ‘--schema’ 옵션으로 요청 형식을 살펴볼 수 있다. ‘--dry-run’을 사용하면 네트워크에 연결하지 않고 요청을 검증할 수 있으며, JSON이나 TOON 형식으로 결과를 출력하거나 ‘--jq’ 옵션으로 필요한 데이터만 추출할 수도 있다.
설치 후에는 제미나이 API 키를 환경변수나 운영체제 키체인에 저장하거나 설정 파일을 통해 등록하면 된다. 구글은 대화형 설정 기능도 제공한다.
제미나이 API CLI는 아파치 2.0 오픈소스 라이선스를 채택해 개발자들이 직접 기여하고 확장할 수 있는 개방형 생태계를 지향한다. 이를 통해 AI 에이전트가 셸 환경에서 도구를 자율적으로 다루기 위한 표준 인터페이스를 제공함으로써, 단순한 개발 보조 도구를 넘어 차세대 AI 에이전트 생태계의 핵심 인프라로 자리 잡을 전망이다.
현재 0.4.x 버전의 실험적 프리뷰 단계로 깃허브를 통해 제공된다. 구글은 개발자 피드백을 바탕으로 도구를 발전시키겠다는 방침이다.

[TOPIC] 에이전트, 개발, 보안, 규제
[SCORE] 7
[REASON] 에이전트 권한 통제는 IAM 정책으로 해야
[FIELD] AI 에이전트
[BODY]
Google recently made Data Agent Kit generally available, moving it out of the preview it ran through the summer. It is free, it is open source, and it installs into coding agents Google does not own. It ships two kinds of control, and the difference matters in production.
Data Agent Kit is a set of MCP tools connecting an agent to more than fifteen Google Data Cloud services, plus Google-authored skills that teach it practices like optimizing BigQuery SQL or designing Bigtable row keys. It runs in Antigravity, Claude Code, Codex, Cursor, and VS Code-compatible editors, and comes preinstalled in Cloud Shell and Cloud Workstations.
Data Agent Kit sits between the coding agent and Google Data Cloud services as two components: skills carrying best-practice guidance and MCP servers exposing live schema and tools. (Source: Google Blog post)
With the GA release, the company adds BigQuery Graph, Bigtable, and Managed Service for Apache Spark. Product manager Arun Nair and developer advocate Jeff Nelson, who wrote the launch post, pitch it at a gap agents have by default: they write good SQL but know nothing about "which tables exist, how they’re partitioned, which ones your team trusts, or why last night’s job failed."
The plugin repository carries 37 skills under Apache 2.0, each with frontmatter naming Google as publisher. It is versioned properly, with 1.0.0 cut on September 29 and 1.1.0 on October 13, so teams can pin it.
Among those skills is accidental-data-loss-prevention, which exists to stop the agent destroying something. Its description opens "STOP AND VERIFY" and tells the agent it "MUST obtain explicit user consent" before anything irreversible, listing DROP TABLE, TRUNCATE, a DELETE missing a WHERE clause or using 1=1, storage deletions against production buckets, gcloud projects delete, and KMS key destruction. The procedure is halt, explain the impact, wait for affirmative consent.
That guardrail is advice. The agent is asked to obey it. A second control is not.
Asked in a LinkedIn post whether read-only investigation could be isolated from tools that modify infrastructure, Nelson answered that it is handled in IAM rather than per agent: run the agent as a read-only service account through impersonation, or use "an IAM deny policy that blocks any MCP tool where tool.isReadOnly is false."
The documentation gives the condition:
api.getAttribute('mcp.googleapis.com/tool.isReadOnly', false) == false
It denies the mcp.googleapis.com/tools.call permission, and applies at the organization, folder, or project level. Companion attributes cover resource.service and tool.name.
Three limits come with it. A blocked tool still appears in tools/list, so the agent sees capabilities it cannot use and finds out only on invocation. The controls cover Google Cloud MCP servers and nothing else. And resource.service and tool.name are gcloud only, absent from the console.
Amel Habira, an AI solutions architect, read the documentation and came away encouraged, noting the short-lived credentials, the read-only attribute, and a warning before agents execute notebook cells. He wrote:
Combine that with branching and time travel on the Iceberg side, and you can imagine containment at both the access layer and the data layer.
Ankit Dongre, an AI engineer at viaSocket, drew the boundary further out:
MCP access is the easy part. The production boundary is permission scope plus repeat-safe execution: what happens when an agent retries a write after a timeout, or when the schema changes mid-run?
IAM and dry runs cover authorization and preflight, he added, "but they do not tell the agent whether a timed-out write committed. A first-class result should carry an idempotency key plus commit status and rollbackability." Data Agent Kit’s tool results do not carry that today.
Microsoft put that decision somewhere else.

웹사이트 개발에 널리 사용되는 프로그래밍 언어 PHP에서 새로운 보안 취약점이 발견됐다. 외부 공격자가 서버에서 임의 코드를 실행하는 데 악용할 수 있는 문제지만 아직 정식 보안패치가 나오지 않았다. 한국인터넷진흥원(KISA)은 해당 취약점에 노출될 수 있는 기업과 기관에 서버 설정을 변경하는 임시조치를 권고했다.

A new UEFI bootkit named BlackX, deployed in an espionage campaign in early 2026, exploited the old Baton Drop vulnerability to bypass Secure Boot and load a malicious driver designed to interfere with security solutions from Kaspersky and Avast.
The operation has been attributed with medium confidence to APT41, a Chinese state-sponsored threat group also known as Brass Typhoon, Wicked Panda, and Barium.
It was discovered in early 2026 and targeted diplomatic agencies in Central Asia, particularly in Tajikistan, Uzbekistan, and Turkmenistan.
Kaspersky researchers analyzed the BlackX bootkit and found similarities with BlackLotus, which has been circulating on hacker forums since October 2022 and leveraged the Baton Drop vulnerability (CVE-2022-21894) to bypass Secure Boot protection.
ESET confirmed in March 2023 that BlackLotus exploited Baton Drop, and at the time it could compromise even fully patched Windows 11 systems.
According to Kaspersky researchers, BlackX's implementation of the exploit is "remarkably similar" to the one used by BlackLotus, allowing the attacker to enroll custom Machine Owner Keys (MOKs) and load arbitrary EFI files to bypass Secure Boot protections.
However, BlackX differs from BlackLotus and deploys a different kernel driver and follow-on payloads. Kaspersky suggests that BlackX was either derived from reverse-engineering BlackLotus or from its source code.
Although the source code for BlackLotus was leaked in July 2023, the release was incomplete. Kaspersky researchers found that some BlackLotus samples they analyzed contained code missing from the public repository but present in the BlackX bootkit.
Since the BlackX operator could not have obtained this code from the leaked repo, the researchers believe the attacker either reverse-engineered BlackLotus or purchased its source code.
BlackX capabilities
BlackX injects a malicious Windows kernel driver signed with a now-revoked certificate issued to an organization named Wenjiang District Mingyu Network Technology Service Studio.
The driver disables security-related processes and registry callbacks, and tampers with Event Tracing for Windows (ETW) providers to obstruct monitoring.
The researchers note that some tampering procedures are configured to run only if Kaspersky or Avast products are detected on the target host, adding that the mechanism is useless against the company's solutions.
The driver also protects the bootkit’s files by intercepting user requests to open them and launching the Windows Calculator instead.
Its purpose is also to deploy the following espionage payloads on infected machines:
- A RAT that uses Google Drive, OneDrive, or Yandex.Disk for command-and-control (C2) to execute .NET payloads and upload and download files.
- OxiDLLRunner, an OLLVM-obfuscated DLL sideloaded by googleupdate.exe. It decrypts v8_context_snapshot.bin to launch shellcode and a Rust payload, which retrieves DLL plugins from archivetj[.]com and executes their ‘create_plugin’ functions in separate threads.
Insufficient fix
Kaspersky says that all BlackX victims used a fully patched Windows release. However, the bootkit was still successful because admins did not manually activate the additional Secure Boot revocations.
“The patch for the Baton Drop vulnerability is designed to revoke the “Windows Production PCA 2011” certificate used to sign vulnerable UEFI components,” Kaspersky explains.
“However, this revocation does not happen automatically upon patch installation - the user has to trigger it manually.”
The researchers say this is a gap in the update process, since it’s extremely uncommon for administrators to take any manual action after applying a security update.
They believe that the attacker used this mitigation gap to their advantage and "decided to invest time in understanding how BlackLotus works and creating a copycat of this bootkit."

블록이 운영하는 스퀘어는 이미 음식 주문을 처리하는 업무에 음성 AI를 활용하고 있다. 자체 음성 모델을 활용하면 외부 AI 서비스에 대한 의존도를 낮추고 매장 주문이나 고객 응대 등 다양한 업무로 활용 범위를 넓힐 수 있다. 다만 블록은 데사를 실제 결제 서비스에 적용할 일정은 밝히지 않았다.
