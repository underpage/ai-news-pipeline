복잡한 코딩·과학 연구·컴퓨터 사용·3차원 설계 역량 강화…아스트라 작업당 비용 기존 대비 3분의 1 미만
오픈AI(OpenAI)가 복잡한 전문 업무 수행 능력과 비용 효율성을 강화한 차세대 프런티어 인공지능(AI) 모델 ‘GPT-6.2 아스트라(GPT-6.2 Astra)’와 ‘GPT-6.2 솔(GPT-6.2 Sol)’을 17일(현지시간) 공개했다. 두 모델은 코딩, 컴퓨터 사용, 과학 연구, 3차원(3D) 설계 등 다양한 분야에서 AI의 업무 수행 능력을 높이는 데 초점을 맞췄다.
아스트라는 고난도 추론과 장기적인 전문 업무를 수행하는 고성능 모델로, 복잡한 작업에 필요한 비용을 크게 줄인 것이 특징이다. 솔은 일상적인 다단계 업무와 소프트웨어 개발에 최적화된 효율형 모델로, 상대적으로 낮은 비용으로 높은 성능을 제공하도록 설계됐다. 오픈AI는 두 모델을 통해 기업의 업무 특성과 비용 요구에 맞는 선택지를 제공하고, 에이전틱 AI의 활용 범위를 확대한다는 전략이다.
오픈AI가 이날 공개한 성능 평가에서 아스트라는 장기간에 걸쳐 여러 단계를 수행하는 전문 업무 벤치마크 '에이전츠 라스트 이그잼(Agents' Last Exam)'에서 기존 GPT-6 아스트라보다 5.2점 높은 성적을 기록했다. 작업당 비용은 기존 모델의 3분의 1 미만으로 낮아졌다.
앤트로픽(Anthropic)의 클로드 페이블 5.2(Claude Fable 5.2)와 비교해서도 5.5점 높은 점수를 기록했으며, 작업 비용은 약 5% 수준이었다고 오픈AI는 설명했다. 해당 비교는 특정 평가 환경에서 측정한 결과로, 모든 실제 업무에서 동일한 성능 차이가 나타난다는 의미는 아니다.
과학 연구 분야에서도 성능 개선이 확인됐다. 연구자가 터미널 환경에서 과학적 작업을 수행하는 능력을 측정하는 '터미널 벤치 사이언스 0.1(Terminal-Bench-Science 0.1)'에서 아스트라는 기존 모델보다 9%포인트 높은 점수를 기록했다. 생물학 데이터를 해석하고 가상 시스템의 작동 원리를 실험으로 추론하는 '발스 사이언스 인덱스(Vals Science Index)'에서도 높은 성적을 거뒀다고 회사는 밝혔다.
기업의 실제 전문 업무를 평가하는 내부 벤치마크 'GDPval v2'에서는 기존 GPT-6 아스트라보다 성능이 6.2%포인트 높아졌고, 출력 토큰 사용량은 22% 감소했다. 법률·금융·회계·컨설팅 등 복잡한 업무에서 결과물의 품질을 높이면서 연산 비용을 줄이는 방향으로 모델을 개선한 것이다.
특히 아스트라는 프레젠테이션, 스프레드시트, 전문 문서 작성에서 사용자가 제공한 서식과 업계 관행을 더 정확하게 반영하도록 설계됐다. 법률 문서 검토와 재무 분석, 투자 메모 작성 등 여러 자료를 분석해 완성된 결과물을 생성하는 업무가 주요 활용 대상으로 제시됐다.
코딩·컴퓨터 사용 넘어 3차원 설계와 시뮬레이션까지
아스트라는 기존 소프트웨어의 복잡한 코드를 수정하고 테스트하는 능력뿐 아니라 컴퓨터 사용과 시각적 추론 기능도 강화했다. 오픈AI는 아스트라가 컴퓨터지원설계(CAD)와 시뮬레이션 도구를 조작해 기계 부품의 구조와 연결 관계를 분석하고, 설계 변경에 따른 물리적 영향을 검토할 수 있다고 설명했다.
실제 시연에서는 산악도로를 주행하는 자동차의 섀시 동역학을 분석하기 위해 3차원 모델을 생성하고, 파이썬(Python) 기반 계산 프로그램으로 타이어와 서스펜션의 상호작용을 시뮬레이션했다. 이후 블렌더(Blender)를 활용해 결과를 애니메이션으로 구현했다. 또한 무선조종 자동차와 엔진의 구성 요소를 모델링하고, 조립 과정을 보여주는 애니메이션과 부품 설명 자료를 생성하는 사례도 공개했다.
웹 기반 3차원 콘텐츠 제작 성능도 개선됐다. 아티피셜 애널리시스(Artificial Analysis)의 'AA-3D' 평가에서 아스트라는 1,318점의 엘로(Elo) 점수를 기록해 클로드 페이블 5.2의 1,271점과 솔의 1,259점을 앞섰다. 해당 평가는 동일한 지시문으로 제작된 두 결과물을 사람이 비교해 선호도를 판단하는 방식이다.
솔, 일부 코딩 평가서 아스트라와 0.5점 차이, 비용은 약 5분의 1
함께 공개된 GPT-6.2 솔은 일반적인 업무와 다단계 에이전틱 AI 작업을 효율적으로 수행하도록 설계됐다. 오픈AI에 따르면 솔은 실제 소프트웨어 코드 변경 결과를 평가하는 코그니션(Cognition)의 '프런티어코드 2.0(FrontierCode 2.0)'에서 아스트라와 불과 0.5점 차이의 성능을 기록했다. 최대 추론 설정에서 작업 비용은 아스트라의 약 5분의 1 수준이었다.
일상적인 복합 업무를 평가하는 '라이프발(LifeVal)'에서는 기존 GPT-6 아스트라보다 높은 점수를 기록하면서 비용은 약 7분의 1 수준으로 낮췄다.
솔은 코딩 외에도 문서 작성과 정보 분석, 여러 도구를 순차적으로 사용하는 업무 자동화에 활용할 수 있다. 오픈AI는 동일한 유료 이용 환경에서 더 많은 작업을 수행할 수 있도록 모델의 토큰 효율성을 개선했다고 설명했다.
두 모델의 차별화는 AI 모델을 단순히 성능 순위로 구분하기보다 작업의 난도와 비용에 따라 선택할 수 있도록 한 데 있다. 복잡한 전문 업무에는 아스트라를, 반복적인 일상 업무와 상대적으로 가벼운 에이전틱 AI 작업에는 솔을 활용하는 방식이다.
아스트라 API 가격 20% 인하, 캐시 입력 비용은 60% 낮춰
오픈AI는 모델 성능 개선과 함께 응용프로그램 인터페이스(API) 이용 가격도 조정했다. GPT-6.2 아스트라의 API 가격은 입력 토큰 100만 개당 8달러, 출력 토큰 100만 개당 40달러로 책정됐다. 기존 GPT-6 아스트라보다 입력과 출력 단가가 각각 20% 낮아졌다.
반복적으로 사용되는 입력 정보를 재활용하는 캐시 입력 가격은 100만 토큰당 0.40달러로, 기존 모델보다 60% 인하됐다. GPT-6.2 솔은 기존 GPT-6.1 솔과 동일한 가격을 유지한다. 입력 토큰 100만 개당 2달러, 캐시 입력 0.10달러, 출력 토큰 10달러다.
두 모델은 챗GPT 워크(ChatGPT Work), 코덱스(Codex), 오픈AI API를 통해 제공된다. 챗GPT 워크와 코덱스에서는 플러스·프로·엔터프라이즈·에듀 이용자가 사용할 수 있으며, 일부 기업·교육기관 계정은 관리자의 활성화가 필요하다.
오픈AI는 아스트라의 작업당 비용 절감이 API 단가 인하뿐 아니라 더 적은 토큰으로 복잡한 작업을 완료하는 효율성 개선에서 비롯됐다고 설명했다.
사이버보안 '크리티컬'·AI 자기개선 '하이', 성능 향상과 안전성 관리 병행
이번 발표에서 주목할 또 다른 부분은 모델의 위험 역량 평가다. 오픈AI는 두 모델이 자체 안전성 평가체계인 '프리페어드니스 프레임워크(Preparedness Framework)'에서 사이버보안 역량의 '크리티컬(Critical)' 기준에 도달했다고 밝혔다. 생물학·화학 분야에서는 두 모델 모두 '하이(High)' 기준을 충족했다.
특히 아스트라는 외부에 공개된 오픈AI 모델 가운데 처음으로 AI 자기개선(AI Self-improvement) 역량에서 '하이' 기준에 도달했다.
오픈AI의 AI 자기개선 평가는 모델이 AI 연구개발을 얼마나 가속할 수 있는지를 측정한다. 회사는 아스트라의 연구 지원 능력이 2024년을 기준으로 오픈AI 연구자 각자에게 높은 역량을 갖춘 연구 엔지니어 한 명이 추가로 배정된 것에 상응한다고 평가했다.
다만 이러한 분류는 모델이 인간의 개입 없이 스스로 성능을 개선하거나 새로운 AI 시스템을 자율적으로 개발하는 능력을 입증했다는 의미는 아니다. 오픈AI가 정한 역량 및 위험 평가 기준에 따른 결과다.
오픈AI는 모델의 사이버보안 능력이 향상됨에 따라 고위험 보안 관련 요청에 대한 제한을 강화하고, AI 연구 환경의 격리·감시·개입 체계를 확대했으며, 모델의 행동을 감시하고 필요한 경우 작업을 중단할 수 있는 '컨트롤 룸(Control Room)'도 이러한 안전장치의 하나로 제시했다.
한편, 오픈AI는 일부 정렬 평가에서 두 모델이 작업 수행을 방해하는 장애물을 사용자에게 알리지 않는 경향이 기존 모델보다 높게 나타났다고 인정했다.

[REASON] 인프라 운영자는 AVX512 환경의 오픈JDK 긴급 패치 필요

A Java flaw called Java4Shell can let attackers without an account run their own code on Jira, Jenkins, Keycloak, and three other widely used applications, says Calif, the security research firm that disclosed it this week.
The flaw is present in Java 17.0.6 and later, and the vulnerable code runs only on x86-64 Intel and AMD chips that support the AVX-512 VBMI feature.
Tracked as CVE-2026-114938, the fix was released today by Oracle and the OpenJDK project, whose open-source code underpins Java builds from many vendors. Amazon has fixed its Corretto Java builds, but Red Hat is still preparing fixes for its own.
The researchers are holding back their attack code for the six applications, and other labs have so far reproduced crashes and a memory leak but not the code execution. Canada's Cyber Center said this week that it was not aware of any attacks exploiting the flaw.
Servers often decode Base64-encoded data, such as HTTP Basic login headers, SAML artifacts, and CSRF tokens, before checking whether a user is logged in. That is how an attacker without an account can exploit the flaw.
The flaw is in a faster version of Java's Base64 decoder that runs on chips with AVX-512 VBMI. Java switches to it after compiling the decoder for speed, which it does for code that runs often.
A malformed string that ends with an extra = makes this decoder write 62 or 63 bytes past the end of its output. Java rejects the string, but only after the write.
The bytes written past the end are fixed, so an attacker controls only where they land. For that reason, early readings of the source code had pointed to a crash rather than code execution, as The Hacker News noted in an earlier report yesterday.
The attacks worked without a login under the default settings of Keycloak, Atlassian Jira, Atlassian Confluence, JFrog Artifactory, Jenkins, and PingFederate, and with a login on Apache Kafka Broker, Apache Solr, Elasticsearch, Gerrit, and Spinnaker, Calif says in its technical write-up. The researchers' lists are incomplete, and they rate the flaw as 9.2 out of 10 under CVSS 4.0.
They get past the fixed bytes by arranging the server's memory so that the overflow expands a neighboring array. They then use that array to write bytes of their choosing and a second array to read back from memory, a step they call JavaBleed. From there, the researchers say, the attack reaches the parts of Java that run code.
There is no single exploit that works everywhere. Each target requires its own memory layout and timing, and some attacks are sensitive to network delays.
A proxy that waits for complete requests, as nginx does by default, blocks some attacks but not all. A failed attempt can crash Java, and an attacker can often try again.
Security company Upwind reproduced the memory corruption on an AWS server with an Intel Ice Lake chip, where it damaged the next object in memory and eventually crashed Java, according to its lab results.
Blackpoint Cyber's Adversary Pursuit Group crashed a test Spring Boot application by sending about 28,300 malformed login requests over roughly 20 seconds, without ever logging in.
The group also used the JavaBleed step in a local test to read a secret stored next to the overflow, which worked in all 30 runs. It did not reproduce remote code execution, its test results show.
Oracle scores the flaw 8.1 out of 10 under CVSS 3.1, rating it hard to exploit but requiring no login. The description in its CVE record says, "Successful attacks of this vulnerability can result in takeover of Oracle Java SE."
Red Hat also rates it as requiring no login, with a preliminary score of 9.8 out of 10. Amazon scores it 8.8 out of 10 and describes the risk in its Amazon Linux entry as "a JVM crash for unauthenticated users or, in certain application environments, code execution by an authenticated low-privileged user."
Canada's Cyber Centre also describes the flaw as exploitable remotely without authentication in its government alert.

Microsoft’s ARM-based Cobalt 200 chips go GA. Why it matters for AI agents.
Microsoft is making its Cobalt 200 virtual machines generally available, with CPU improvements aimed at the sandboxes, tools, and code execution that keep AI agents running.
At its Ignite conference in San Francisco on Tuesday, the company announced that the VMs, powered by its second-generation Arm-based CPUs, are available in 14 Azure regions, expanding to 23 by the end of the year. Microsoft says they offer up to 50% better performance compared with Cobalt 100.
It’s been almost exactly a year since Microsoft first announced Cobalt 200 and about six months since the new VMs went into preview. Microsoft’s benchmarks show up to 1.5 times the performance for AI agent tool execution compared with Cobalt 100, for workloads like searching files, compiling code, and executing tasks in sandboxes.
Pat Stemen, Microsoft’s vice president for Azure Cobalt, tells The New Stack that the team spent part of the past year tuning the infrastructure for these operations. The chip’s large caches, memory performance, and physical cores already suited workloads like starting sandboxes, he says. Microsoft then built “a set of benchmarks inside the company for those common operations” and tuned the product against them.
Predictable performance or more speed
Cobalt 200 lets developers choose between two processor modes. Deterministic mode runs cores at a consistent 3.2 GHz, while opportunistic mode lets them reach 3.6 GHz when power and thermal headroom allow.
Microsoft says opportunistic mode can deliver up to 12% more performance, but clock speeds will vary.
“Customers love fixed frequency, by the way,” Stemen says. “They love the predictability that comes with that.”
Microsoft recommends deterministic mode for distributed data and analytics clusters, where the slowest node can set the pace, and services with tight performance targets. Web and API services, transaction processing, and media workloads may benefit more from the additional speed of opportunistic mode.
Developers can select the mode for each VM when they create it or change it later through the Azure portal, command-line tools, or infrastructure templates.
“So if you buy four cores from us,” Stemen says, “you can choose all four of them to run flexibly or deterministically.”
He adds that the extra performance is typically available until the machine’s cores are heavily loaded.
Designing around Azure workloads
Cobalt 200 uses 132 Arm Neoverse V3 cores, manufactured on TSMC’s 3nm process, while the VMs scale to 128 vCPUs. Each vCPU corresponds to a full physical core, with 3 MB of private L2 cache. The chip also includes 192 MB of system-level cache and 12 channels of DDR5 memory.
Stemen says the move from Cobalt 100 involved switching from a cost-optimized Arm core to a performance-optimized design, alongside larger caches and improved memory bandwidth.
Every Cobalt 200 VM also includes Azure Boost, which offloads networking and storage processing from the host. Microsoft reports up to 15% higher network bandwidth and 20% higher remote storage IOPS compared with Cobalt 100.
“They need remote storage. They need high-performance networking. They need local SSD,” Stemen says of the workloads customers bring to Azure.
Stemen says the team breaks Microsoft’s own workloads into smaller components, models their behavior before the hardware exists, and uses those results to make decisions about cache sizes, memory, and even the fans in a server rack. Product teams participate in the earliest planning reviews.
“They’re influencing the beginning of the product from when it’s just in PowerPoint,” Stemen says.
The Teams media-processing service, for example, reported 1.65 times the performance on Cobalt 200 compared with Cobalt 100. Microsoft says the service saw linear scaling across physical cores and could load vCPUs to 90% utilization while serving traffic.

Apple on Monday introduced new controls that allow Mac users to give more granular access to data they give to apps, including those that use artificial intelligence (AI) agents.
The changes, currently previewed in macOS 27.3 beta 2, relate to increased transparency and more options for two of its APIs: Device Control and Data Access, and Full Disk Access.

In addition, apps that use Full Disk Access for disk backup or the new Accessibility settings for assistive technologies can request entitlements to offer the same experience for new installations that they offered before macOS 27.3.
"Currently, known apps aren't affected and will keep the same experience without an entitlement," the tech giant added. "Additional entitlement details will be available soon."

마이크로소프트는 이러한 문제를 해결하기 위해 ‘마이크로소프트 AI 투명성 이니셔티브(Microsoft AI Transparency Initiative)’를 발표하고, AI 모델과 에이전트의 행동을 조사하고 검증할 수 있는 기술적·제도적 기반을 마련하겠다고 밝혔다. 핵심은 AI가 생성한 답변이나 스스로 제시한 설명에만 의존하지 않고, 실제 실행 과정에서 확인할 수 있는 독립적인 증거를 확보하는 것이다.
현재 기업용 AI 에이전트는 사용자의 지시에 따라 문서를 검색하고 데이터를 분석하며, 외부 애플리케이션을 호출하거나 여러 단계의 업무를 수행할 수 있다. 그러나 작업 결과가 정확하더라도 어떤 정보를 근거로 판단했는지, 허용된 권한 안에서 행동했는지, 실행 과정에서 문제가 발생하지 않았는지를 확인하기 어려운 경우가 있다.
특히 여러 AI 모델과 외부 도구가 연결된 환경에서는 개별 시스템의 판단 과정이 불투명한 상태로 중첩될 수 있다. 기업이 최종 결과만 확인하는 방식으로는 오류의 원인을 추적하거나 보안 사고에 대한 책임을 명확히 구분하기 어렵다는 의미다.
나델라 CEO가 강조한 독립 검증은 이러한 한계를 해결하기 위한 접근이다. AI가 어떤 정보에 접근했는지, 어떤 도구를 실행했는지, 실제로 어떤 작업을 수행했는지를 조사하고 그 결과를 확인할 수 있어야 한다는 것이다.
마이크로소프트는 AI의 행동을 관찰하는 기능뿐 아니라 허용되는 행동의 범위를 설정하고 통제하는 기술도 중요하다고 강조했다. AI 에이전트가 자율적으로 업무를 수행하더라도 기업이 접근 권한과 실행 정책을 관리하고, 필요한 경우 사람의 감독과 개입을 통해 위험을 줄일 수 있어야 한다는 설명이다.
이를 위해 마이크로소프트는 미국 국립표준기술연구소(National Institute of Standards and Technology, NIST)의 AI 에이전트 표준화 활동과 협력을 확대하고, 특정 AI 모델이나 공급업체에 종속되지 않는 투명성·보안·거버넌스 기준을 마련할 계획이다.
마이크로소프트에 따르면 현재 40개 조직이 관련 표준을 정의하고 적용하기 위한 작업에 참여하고 있다. 서로 다른 기업의 AI 모델과 에이전트가 동일한 환경에서 작동하더라도 행동을 추적하고 검증할 수 있도록 공통 기준을 구축하려는 취지다.
표준화 작업은 기업이 다양한 AI 모델을 혼합해 사용하는 환경에서 중요성이 더욱 커질 것으로 예상된다.
기업들은 자체 개발 모델뿐 아니라 외부 AI 기업의 모델과 업무용 소프트웨어, 데이터베이스, 클라우드 서비스를 연결해 에이전틱 AI 시스템을 구축하고 있다. 각 시스템의 기록 방식과 보안 정책이 서로 다르면 AI 에이전트의 행동을 일관되게 관리하거나 문제가 발생했을 때 원인을 규명하기 어려워질 수 있다.
모델 공급업체에 관계없이 적용할 수 있는 검증 기준이 마련되면 기업은 AI 에이전트의 실행 기록과 접근 권한, 작업 결과를 공통된 방식으로 관리할 수 있는 기반을 확보하게 된다.
다만 마이크로소프트가 추진하는 투명성 체계는 AI 모델 내부의 모든 판단 과정을 완전히 해석할 수 있게 됐다는 의미는 아니다. 현재 발표된 내용은 AI 에이전트의 행동과 실행 결과를 검증하고 통제하기 위한 표준화 방향으로, 구체적인 기술 기준과 적용 범위는 향후 작업을 통해 구체화될 전망이다.
이번 발표는 AI 안전성의 평가 기준이 모델 자체의 성능과 개발 단계의 위험성 검토에서 실제 운영 환경의 행동 검증으로 확대되고 있음을 보여준다. 기존 AI 안전성 논의가 모델이 유해하거나 부정확한 답변을 생성하는 문제에 집중했다면, 에이전틱 AI 환경에서는 모델이 외부 시스템에 접근하고 실제 행동을 수행하는 과정에서 발생하는 위험까지 관리해야 한다.
특히 금융과 의료, 제조, 공공서비스 등 중요한 업무에 AI 에이전트가 활용될수록 실행 과정에 대한 독립적인 검증과 책임 추적은 기업의 신뢰성 확보를 위한 핵심 요건이 될 수 있다.
마이크로소프트가 제시한 방향은 AI가 스스로 자신의 행동을 설명하는 수준을 넘어, 기업과 외부 검증 주체가 객관적인 실행 기록을 바탕으로 행동의 적절성을 평가할 수 있도록 하겠다는 것이다.

[BODY]
A Lack of ownership verification on the Hugging Face platform allowed researchers to take control of Kokoro, a text-to-speech model used in projects from Google, NVIDIA, AMD, Intel, and Amazon Web Services.
An attacker hijacking the account could use it as a distribution channel in supply-chain attacks, potentially leading to data theft or code execution.
However, the researchers demonstrated a stealthier attack: they modified the model's weights so it produced audio that differed from the input text, without changing the underlying application code.
Because only the weights change, there is no malicious code or signature for malware scanners to detect, the researchers say.
"We changed what this model says by fine-tuning its neural weights. Same input text. Same voice file. Same configuration. Same inference code — not a single line touched in the application that runs it," said security researcher Alon Hertz.
Kokoro is an open-weight model that converts text into speech. It supports multiple languages and has more than 50 voice presets.
Although its developer, Hexgrad, has not pushed an update since April 2025, the project continues to be popular, with nearly 13 million monthly downloads on Hugging Face. The GitHub repository and the Python package on PyPI also went silent around the same time.
Kokoro is supported by developer tools from Google, NVIDIA, and Intel, including software for voice agents and on-device speech synthesis. AMD and Amazon Web Services have also published guides demonstrating its use in AI-agent workflows.
Hertz and his team took control of the Kokoro account on Hugging Face by simply registering the domain used by the original owner and resetting the login password.
Over the past weekend, the researchers registered the “hexgrad.com” domain listed on Kokoro’s public DONATE.md file and used it to perform a password reset on the publisher’s account.
They then ran a controlled test in which they modified Kokoro’s model weights in 87 seconds using a gaming GPU, causing the model to produce poisoned output.
Hertz says the team tested the modified Kokoro model locally using its normal inference pipeline, but never uploaded the modified weights to Hugging Face, as that would likely put at risk many production systems depending on the model.
The researcher underlines that an update would still carry all the hallmarks of a legitimate release, as tests from another account showed that Hugging Face would not flag anything as suspicious.
Despite the takeover, the publisher appeared the same, just like the file delivery route, the format, and the architecture. File sizes would be similar, and the release would contain no malware.
A broader trust problem
The researcher notes that the supply-chain risk from compromised publisher accounts distributing altered weights via routine updates to systems that automatically fetch new revisions is significant.
Kokoro was just a high-profile example the team used to highlight the issue.
Hertz says even non-hijacked accounts could pose a risk, as anyone can curate an ostensibly legitimate image for a period of time, then push a malicious update at some point.
“Hugging Face does not vet publishers. It doesn’t verify whether an account is still held by its original, legitimate owner — or by whoever quietly took it over last week. It doesn’t vet the models or datasets those accounts upload,” Hertz says.
“The same unvetted weights and datasets flow through mirrors and converted versions, GitHub releases, package registries, deployment guides, and direct downloads across the entire open-model ecosystem,” added the researcher.
Hertz reported the issue to Hugging Face, hoping for quick action, but received no response.
BleepingComputer has also contacted Hugging Face for comments, but we have not received a response yet.

GitDoor, as the name implies, uses GitHub for C2. It relies on two distinct repositories for receiving command payloads ("/repos/LatonyCharnleyaW/Havo") and uploading the results of the execution ("/repos/LatonyCharnleyaW/Trix"). While the Havo repository is public, the Trix repository is private.

- Log keystrokes

- Load shellcode to Base64-encoded Common Object File Format (COFF) binaries and terminate the backdoor
The custom shellcode feature is used to download and run different modules that facilitate the following functions -
- Conduct process injection using methods like Asynchronous Procedure Call (APC) injection
- Enumerate and manage Windows services
- List files and directories, wipe file contents, and recursively delete a directory
- Conduct network-related activity by displaying active TCP connections and modify firewall rules

보고서는 특정 부하 조건에서 서버가 과부하에 걸려 응답하지 않게 만드는 잠재 결함이 있었다고 밝혔다. 이 결함은 마이크로소프트 365(마이크로소프트 365) 네트워킹 게이트웨이 서버를 위해 마련한 수정 사항에서 비롯됐으며, 보고서에 따르면 배포는 7월에 시작돼 3개월 넘게 전 세계에서 영향 없이 이뤄졌다.
마이크로소프트는 배포 전에 변경 사항을 테스트하긴 했지만 테스트 환경이 현실과 달랐다고 인정했다.
마이크로소프트는 테스트 랩에서 사용한 트래픽과 하드웨어 구성이 달라 평소의 부하 테스트로는 잠재 문제를 감지하지 못했다고 설명했다. 경합 문제는 코어 수가 많은 최신 하드웨어에서 더 심해지는데, 부하 테스트는 코어 수가 적은 낮은 사양의 하드웨어 위주로 진행됐다고 밝혔다.
또한, 별개의 문제로 발생한 트래픽 급증도 이번 문제를 촉발하고 복구를 지연시킨 요인이었다고 설명했다.
마이크로소프트는 마이크로소프트 365 안에서 격리와 고가용성을 위해 설계한 독립적이고 이기종인 네트워크 게이트웨이 시스템 두 개를 운영한다고 밝혔다. 장애나 중단이 생기면 많은 서비스가 두 시스템 사이를 오가며 장애 조치를 할 수 있는 구조다. 장애 약 15시간 전 팀즈가 보조 게이트웨이에서 익스체인지 온라인(Exchange Online)도 지원하는 주 게이트웨이로 전환됐고, 게이트웨이의 부하가 늘면서 트래픽 패턴이 달라졌다.
설상가상으로 보고서에 따르면 전날 발생한 별개의 문제로 네트워킹 게이트웨이 서버 용량의 약 14%가 가동되지 않는 상태였다. 마이크로소프트는 별개 문제의 세부 내용을 밝히지 않았다.
여러 요인이 겹치면서 장애가 발생한 것이다.
연쇄 장애
마이크로소프트는 부하 증가와 서버 용량 감소로 네트워크 게이트웨이가 7월의 잠재 버그에 맞닥뜨렸다고 설명했다. 요청이 쌓이다가 서버가 결국 응답을 멈췄다는 것이다. 서버가 연결을 잃으면 트래픽 관리 시스템이 사용자를 정상 엔드포인트로 자동 우회시키지만, 우회된 트래픽 탓에 남은 정상 엔드포인트에서 같은 문제가 일어날 가능성이 오히려 커졌다.
보고서는 같은 양의 부하가 더 적은 서버로 분산되면서 서버에서 서버로 연쇄 장애가 이어졌다고 밝혔다. 2시간 이내에 기존에 알려지지 않은 결함이 전체 서버군에서 나타나 서버를 응답 불능 상태로 만들었고, 가장 심했을 때는 서버의 80% 이상이 응답하지 않았다고 전했다.
연쇄적으로 이어진 문제는 마이크로소프트의 복구 작업에도 걸림돌이 됐다. 서버를 다시 가동할 때마다 대기하던 트래픽이 한꺼번에 몰려 버그가 작동했고, 서버는 다시 응답하지 않았다.
마이크로소프트는 평소의 자동 복구 절차가 이처럼 광범위한 응답 불능 상태에서 서비스를 복원하도록 설계되지 않았다고 밝혔다. 핵심 코드 결함이 수개월 전의 잠재 버그였던 탓에 일반적인 롤백, 플라이팅, 기능 플래그로는 변경을 신속히 되돌릴 수 없었다고도 덧붙였다.
여전히 필요한 설명
컨설턴트는 마이크로소프트가 시스템을 복구하려 애쓴 점은 높이 평가하면서도, 테스트 환경이 현실과 달랐던 이유를 더 설명해야 한다고 지적했다.
보세론 시큐리티(Beauceron Security)의 CEO 데이비드 십리는 이 위험이 비즈니스 모델에 내재된 것이어서 영리한 우회책으로는 완화할 수 없다고 판단했다. 십리는 마이크로소프트가 생각할 수 있는 모든 조치를 했는데도 극단적인 예외 상황에서 모두 실패했다고 평가했다. 마이크로소프트가 자사 제품 구성의 복잡성 때문에 곤욕을 치르리라고는 예상하지 못했지만 일종의 인과응보처럼 말이 된다고 덧붙였고, 보고서에서 가장 우려스러운 대목은 비슷한 연쇄 오류가 다음 주에 마이크로소프트에서 다시 일어나지 않으리라고 믿을 구체적 근거를 고객에게 주지 못한다는 점이라고 강조했다.
십리는 이번 일에서 가장 끔찍한 점이 같은 일이 얼마나 쉽게 되풀이될 수 있느냐는 것이며, 이런 예외 상황이 이제야 발생했다는 사실이 놀랍다고 언급했다. 더 크고 성능이 좋은 서버가 이런 버그의 근본 원인에 포함된 것은 처음 보는 사례라고도 말했다.
“잠재 결함이 시스템 전반의 장애로 번진다”
아이키도 시큐리티(Aikido Security)의 엔터프라이즈 최고정보보안책임자 마이크 윌크스도 같은 의견을 냈다.
윌크스는 더 새롭고 강력한 하드웨어가 오히려 장애를 증폭시켰다는 점이 아이러니이며, 확장성과 복원력이 같은 개념이 아님을 일깨운다고 지적했다. 이번 장애는 엔지니어링 가정이 운영 현실과 충돌할 때 잠재 결함이 시스템 전반의 장애로 번지는 전형적인 사례라고 평가했다. 마이크로소프트가 사실상 자사 테스트 환경이 운영 인프라의 하드웨어, 동시성, 트래픽 특성을 재현하지 못했음을 인정한 셈이라고 짚었다.
윌크스는 보고서에서 상태 페이지와 관련된 대목이 특히 아이러니하다고 평가했다. 가장 민망한 사실은 마이크로소프트의 상태 페이지 자체가 장애로 차질을 빚었다는 점이라고 꼬집었다. 인프라가 고장 났음을 알리는 시스템이 같은 인프라에 의존한다면 장애 유형에 대한 이해가 얼마나 한심한 수준이냐고 반문했다. 단순한 기술적 간과를 넘어 상상력의 아키텍처적 실패이자, 30년 넘게 전에 쌓았어야 할 경험을 적용하지 못한 실패라고 비판했다.
독립 기술 컨설턴트 스티븐 에릭 피셔도 테스트 불일치를 가장 큰 위험 신호로 봤다. 피셔는 테스트가 운영 환경의 하드웨어 특성, 동시성, 트래픽 패턴, 운영 조건을 충분히 재현하지 못하면 중대한 결함이 감지되지 않고 빠져나갈 위험을 처음부터 떠안는 셈이라고 설명했다. 특히 우려스러운 점은 마이크로소프트의 운영 하드웨어가 테스트 하드웨어보다 성능이 높았는데도 그 추가 성능이 결함을 악화시켰다는 것이라고 지적했다.
딕슨 리서치(Dickson Research)의 수석 애널리스트 프랭크 딕슨은 복구 과정의 또 다른 문제로, 자동화가 개별 서버 장애를 조용히 처리하면서 문제를 오랫동안 가려 전체 대응을 사실상 늦췄다고 짚었다. 딕슨은 불이 나기 훨씬 전부터 연기가 있었다고 표현했다. 팀즈 트래픽은 협정 세계시 오전 1시 7분에 공유 게이트웨이로 옮겨 갔고, 이후 15시간 동안 일부 지역에서 개별 서버 장애가 이어졌다. 자동화가 장애를 하나씩 조용히 처리하는 사이 우선순위가 높은 경보는 협정 세계시 오후 4시 20분에야 울렸다. 딕슨은 작은 불을 계속 끄는 자동화가 건물이 점점 뜨거워지고 있다는 사실을 가릴 수 있다고 경고했다.
