[REASON] 중국산 칩으로 학습한 1.6조 규모 에이전트형 모델 공개
[FIELD] AI 모델
[BODY]
메이투안이 중국산 AI 반도체로 학습한 1조6000억 매개변수 규모의 멀티모달 AI 모델 '롱캣-2.5(LongCat-2.5)'를 공개했다. 복잡한 소프트웨어 개발과 시각적 디자인, 3D 콘텐츠 제작 등을 지원하는 에이전트형 모델로, 이전 버전보다 장시간 작업 수행 능력을 크게 높였다.
메이투안은 2일(현지시간) 롱캣-2.5의 기술 성과를 공개하고 API 서비스를 시작했다고 밝혔다.
전체 매개변수는 1조6000억개지만, 전문가 혼합(MoE) 구조를 활용해 토큰당 약 480억개만 활성화한다. 기존 롱캣-2.0과 모델 규모는 같지만 시각 정보 이해와 에이전트형 코딩 능력을 강화했다.
특히 복잡한 코딩 작업에서 성능 개선이 두드러졌다. 메이투안 자체 평가에서 '터미널벤치 4.0' 점수는 기존 3.0점에서 38.5점으로, '딥SWE 1.1'은 9.7점에서 64.6점으로 높아졌다. 웹 검색을 통한 문제 해결 능력을 평가하는 '브라우즈컴프'에서도 79.9점에서 91.9점으로 상승했다.
경쟁 모델과 비교하면 일부 평가에서는 최고 수준의 성능을 기록했다. 브라우즈컴프에서는 '클로드 오퍼스 5'의 90.8점과 'GPT-5.6 솔'의 90.4점을 앞섰으며, '3D코드벤치'에서도 55.4점으로 비교 모델 중 가장 높은 점수를 얻었다.
다만 복잡한 코딩 작업을 평가하는 터미널벤치 4.0에서는 클로드 오퍼스 5의 53.9점에 미치지 못했다. 이 수치는 메이투안이 공개한 평가 결과로, 일부 경쟁 모델 점수는 자체 측정한 것이다.
성능 개선에는 대규모 장기 강화학습(RL)이 활용됐다. 실제 소프트웨어 개발 과정에서 AI 에이전트가 실패한 사례를 수집하고, 이를 재현 가능한 학습 과제로 전환했다. 깃허브의 코드 수정 요청과 관련 문제를 바탕으로 학습 환경과 검증 테스트를 자동 생성해 모델의 부족한 기능을 보완하는 방식이다. 반복적인 추론과 불필요한 도구 호출을 줄이는 학습 기법도 적용했다.
멀티모달 처리 방식도 개선했다. 이미지와 같은 시각 정보를 여러 단계의 디지털 토큰으로 변환해 텍스트와 동일한 모델 구조에서 통합적으로 처리한다. 기존처럼 시각 정보와 언어 정보를 별도로 다루는 방식과 달리, 두 정보를 결합한 복잡한 작업을 효율적으로 수행하도록 설계했다.
이를 활용해 웹페이지 디자인과 3D 모델, 인터랙티브 콘텐츠를 제작할 수 있다. 메이투안은 실시간 유체 시뮬레이션을 구현하는 웹페이지와 3D 유물을 회전·확대하며 살펴볼 수 있는 디지털 전시 페이지 등을 시연했다. 기업의 사업 데이터 분석과 수익률 계산, 고객 피드백 분류 및 보고서 작성 등의 업무도 지원한다.
이번 모델은 중국산 AI 가속기를 활용했다는 점에서도 주목된다. 메이투안은 지난 6월 롱캣-2.0을 중국산 AI 반도체로 학습한 데 이어 이번에도 자국산 연산 인프라를 활용했다. 다만 사용한 반도체 제조사와 구체적인 제품명은 공개하지 않았다.
특히 중국산 가속기의 메모리와 연산 특성에 맞춰 장문맥 학습과 추론 시스템을 최적화했다. 모델 가중치와 연산 데이터를 각각 4비트로 압축하는 W4A4 양자화 기술을 적용해 메모리 사용량과 연산 비용을 줄였다. 그 결과 기존 8비트 방식보다 입력 처리량은 43.3%, 출력 생성 처리량은 42.77% 증가했다고 밝혔다.

[BODY]
인공지능이 침해된 조직의 내부망에서 공격 도구와 명령을 선택하고, 실행 결과를 분석해 다음 단계를 결정하는 실제 해킹 사례가 공개됐다. 공격자가 AI 기반 도구를 설치한 뒤 도메인 관리자 계정을 탈취하기까지 걸린 시간은 3~4일이었다.
카스퍼스키는 11월 2일 공개한 연구에서 아프리카와 중남미 지역 교육기관을 대상으로 오픈소스 침투시험 프레임워크 ‘사이버스트라이크AI(CyberStrikeAI)’를 악용한 공격을 확인했다고 밝혔다. 공격은 2026년 9~10월 관측됐으며, 내부망 정찰과 인증정보 탈취, 시스템 간 이동, 데이터 수집 과정에 AI가 활용됐다.
초기 침투는 사람이 수행…AI 도입 후 관리자 계정 장악
연구진이 재구성한 사고에서 공격자는 이미 침해된 SQL 서버를 통해 수동으로 시스템 정보를 수집하고 공격 도구를 준비했다. 약 2주간 활동이 중단된 뒤 피해 시스템에 사이버스트라이크AI 임플란트가 설치됐다.
이후 도메인 관리자 계정이 침해되기까지 3~4일이 걸렸다. 도메인 관리자 계정은 조직의 윈도 시스템과 사용자 계정을 광범위하게 관리할 수 있는 고권한 계정이다. 마지막 단계의 시스템 간 이동과 인증정보 수집, 데이터베이스 내보내기는 1시간 이내에 진행됐다.
따라서 ‘3~4일’은 최초 침투부터 계산한 전체 공격 기간이 아니라, 사이버스트라이크AI 임플란트 설치 이후 관리자 계정 침해까지의 시간이다. 최초 접근부터 모든 과정이 AI만으로 수행됐다는 의미도 아니다.
공격자 서버의 AI가 판단…피해 시스템은 명령 실행
사이버스트라이크AI는 명령제어 시스템과 거대언어모델(LLM)을 결합한 침투시험 프레임워크다. 사람이 공격 목표를 지정하면 모델이 도구를 선택하고 명령을 생성하며, 실행 결과를 분석해 후속 작업을 결정하는 구조다.
피해 시스템에 설치된 임플란트는 전달받은 명령을 실행하고 결과를 공격자 서버로 반환했다. AI는 공격자 측 서버에서 작동했으며, 피해 시스템의 임플란트가 AI 모델을 직접 실행하거나 외부 AI 서비스에 직접 요청을 보내는 방식은 아니었다.
중국어 주석만으로 배후 판단 불가…행위 중심 탐지 필요
카스퍼스키는 공격 스크립트에서 중국어 주석을 발견했지만, 이를 근거로 특정 국가나 알려진 공격조직과의 연관성을 확정하지 않았다. 발견된 인프라 전체가 동일한 운영자의 통제 아래 있었는지도 확인하지 못했다.
탐지 과정에서는 인증정보 추출과 악성 예약작업 생성, 사이버스트라이크AI의 C2 통신, 도메인 구조를 파악하기 위한 의심스러운 질의가 확인됐다. 국내 기업과 대학도 이러한 행위를 관리자 계정 활동과 연계해 점검할 필요가 있다.
이번 사례는 공격자가 초기 침투에 성공한 뒤 AI를 이용해 내부망 장악 과정을 자동화했음을 보여준다. 방어 측에서는 AI 도구의 사용 여부와 함께, 인증정보 탈취와 권한 확대 등 실제 침해 행위를 조기에 발견하고 차단하는 역량이 중요해졌다.

[FIELD] 보안
[BODY]
AI coding agents are installing MCP servers that will never be patched
When a developer tells an AI coding agent to “set up a GitHub MCP,” the agent has to pick a package. New research from Glow Labs documents sessions where it picked one out of an archived repository that will never be patched again.
Source: Glow Security
Reviewing real AI coding session transcripts, Glow Labs found deprecated MCP servers landing on developer machines, a pattern it calls MCPhantom. In 98% of those sessions, the agent appears to have filled in the name from the model’s training data. In the other 2%, the user asked for the old package by name. The research looked only at sessions where a deprecated server was installed or suggested.
GitHub maintains an MCP server of its own. In the GitHub example Glow Labs documents, the agent passed over it for a deprecated Anthropic reference server from its training data. The repository is archived and says no security updates are coming, but agents don’t read archive notices.
The same pattern showed up across Claude Code, Cursor, Codex CLI, Claude Cowork and Claude chat, and models from Anthropic, OpenAI and xAI.
Four flaws, no patches
Four high-severity vulnerabilities turned up in those reference servers. The most serious is a remote code execution bug in the Puppeteer server, which lets an agent drive a browser. A prompt injection is all it takes. The agent starts any process on the machine instead of the browser, and runs any command the attacker chooses. The developer approved web browsing, and that one permission stretches to cover the rest, so the harness lets it through.
Glow Labs’ report was closed as out of scope, and the maintainers replied that the server was archived in May 2025 and is unmaintained, so no fix will come from that repository. They did say they would look at marking the npm package deprecated so users get a warning, but a deprecated package still installs through npx. No exploitation has been seen yet, and no patch is coming either.
Usage hasn’t followed the deprecations. The deprecated packages Glow Labs counted have been downloaded from npm more than 17.3 million times since July 2025, with five of them in npm’s top MCP 100.
Why existing controls stay quiet
These servers are dependencies that never appear in a dependency file. EDR watches a trusted Node process install a public npm package at the agent’s request, which looks routine. SCA has no manifest, since the server runs through npx, and the flaws have no CVEs. Software inventory never registers an application, so the endpoint is the only place it shows up.
Asking the agent to look things up first isn’t the answer either. “A lookup before install is not enough on its own,” Nadav Claude Cohen, vulnerability researcher at Glow, told Help Net Security. “In one session the agent checked the package on npm and got back ‘This package is deprecated.’ It installed the package anyway and never told the user.”
Who can fix this
Cohen sees four possible sources of a fix:
- Harness makers could refuse deprecated servers, or at least warn the operator, and cover the ones already installed rather than only new installs, but “it works only if every harness does it. If one harness fixes it, the others stay open.”
- Model makers could update what the models know: “as long as the models’ knowledge contains the old package names, agents will keep installing them,” though “updating model weights is very expensive, so this is unlikely to happen.”
- The package owners could fix the bugs, “the only fix that protects people who keep using these servers.”
- Security companies can use the pre-execution hooks many harnesses already support: “This works today, without waiting for the harness makers, the model makers or the package owners.”
Pulling the packages isn’t an option. npm lets an owner remove one only if it had fewer than 300 downloads in the past week, has a single owner and no public dependents.

[REASON] PyTorch를 구글 TPU에서 네이티브로 쓰는 오픈소스
[FIELD] 신기술
[BODY]
TorchTPU is an open-source project developed by Google in collaboration with Meta that provides a native PyTorch backend for Google TPUs. It enables PyTorch workloads to execute on TPU hardware with minimal code modifications, supporting eager and compiled execution, distributed computing, and hardware-specific optimizations.
Google began enabling PyTorch workloads to run on TPUs in 2020 through PyTorch/XLA, which leveraged JAX, XLA, and lazy tensors. According to Google, this approach had significant shortcomings:
Crucially, PyTorch/XLA required intrusive source-code modifications to explicitly define compilable regions, suffered from severe compile-time latency, lacked support for PyTorch's native imperative (“eager”) execution mode, and lagged in supporting emerging distributed computing primitives within the PyTorch ecosystem.
TorchTPU takes a fundamentally different approach, making eager execution a top priority, and enabling existing PyTorch workloads to run out with minor code modifications.
Specifically, migrating from GPUs to TPUs involves replacing the cuda device with tpu and the nccl distributed backend with tpu_dist. Alternatively, developers can use the new torch.accelerator.current_accelerator API to identify the available accelerator, as shown in the following snippet.
import torch
import torch.distributed as dist
def main():
    device = torch.device("cuda") # -> device = torch.accelerator.current_accelerator
    dist.init_process_group(backend="nccl") # -> dist.init_process_group()
    rank = dist.get_rank()
    word_size = dist.get_world_size()
    ...
    model = model.to(device)
    ...
TorchTPU support three eager execution modes: strict, debug, and DeferAndFuse. The latter is a new hybrid eager/compiled execution mode that Google claims "can be 50% or more faster than Strict Eager while reducing peak HBM memory".
To test TorchTPU's ability to run existing PyTorch models with no modifications, Google built an integration pipeline to evaluate about 5,000 Hugging Face models across 500+ architectures in both eager and compiled modes on TPU hardware generations starting from v5e.
We use a robust testing methodology grounded in corpus stratification and balanced architectural selection. Our approach relies on a two-tiered selection process designed to balance real-world adoption with broad architectural diversity, avoiding redundant testing of minor variations while ensuring real production weights are thoroughly evaluated.
To validate TorchTPU's performance, Google ran a 30-billion parameter Muse Glimmer model implemented in standard PyTorch. On a single TPUv7 chip, inference throughput reached 25.7k token/s at 5120 sequence length and 22.4k token/s at 10,240 sequence length. For training, using four TPUv7 chips, throughput reached 5.6k token/s and 4.6k token/s at 5120 and 10,240 sequence length, respectively.
Google also conducted experiments using Qwen3 MoE 235B for training workloads, scaling from 1,024 to 8,192 TPUv7 chips. For inference, Google reported competitive performance-per-dollar for large-scale MoE workloads using vLLM.
Commenting on the announcement, Hacker News user tingkuanpei observed:
Very interesting work. Google should have done this a long time ago. PyTorch's ecosystem is just so rich.
Other users pointed out that beyond offering TPUs through GCP, Google sells them to "enterprise client for on premises deployments", which include Anthropic and in Meta following potentially in the future.
TorchTPU is still at an early stage and therefore in continuous evolution. The project's roadmap include work on dynamic shapes, compilation performance, operator coverage, reinforcement learning, and quantization. For further details, make sure to read the original announcement, which provides a more comprehensive view of TorchTPU's architecture and scope.

기존 음성 에이전트는 음성 인식(STT), 발화 구간 감지, 대화 차례 전환, 대규모언어모델(LLM), 음성 합성(TTS) 등을 각각 선택하고 연결해야 했다. 각 기술의 성능과 응답 시간을 조정하는 과정도 필요했다. 일레븐 리얼타임은 이러한 기능을 하나의 시스템으로 통합한 것이 특징이다. 개발자는 개별 구성 요소를 조합하는 대신 목적에 맞는 모델을 선택해 음성 에이전트를 구축할 수 있다.
v1 미니는 AI 비서와 교육용 튜터, 게임 속 대화형 캐릭터 등 빠른 상호작용이 중요한 서비스에 적합하다. v1 맥스는 고객 지원, 잠재 고객 선별, 외부 도구를 호출하는 다단계 업무 등 복잡한 추론과 작업 수행이 필요한 환경을 겨냥한다. 두 모델 모두 한국어와 일본어를 포함한 90개 이상 언어를 지원하며, 1만7000개 이상의 음성 라이브러리를 활용할 수 있다. 대화 도중 사용자가 끼어드는 상황에 대응하고 자연스럽게 발화 순서를 조정하는 기능과 도구 호출도 지원한다.
일레븐랩스가 공개한 아티피셜 애널리시스의 2026년 10월 평가 결과에 따르면, v1 맥스는 음성 기반 추론 벤치마크 ‘빅 벤치 오디오’에서 98.8%의 정답률을 기록했다. 질문이 끝난 뒤 첫 답변을 시작하기까지 걸린 시간은 평균 0.57초였다.
대화 중 침묵과 발화 순서 전환, 끼어들기 대응 등을 측정하는 풀 듀플렉스 벤치에서는 v1 미니가 95.8%, v1 맥스가 94.1%를 기록했다. 빠른 대화 반응이 중요한 환경에서는 미니가, 복잡한 음성 추론과 업무 처리에서는 맥스가 각각 차별화한 성능을 보인 셈이다.
개발자는 일레븐 에이전트에서 모델을 선택하거나 리얼타임 API를 통해 서비스를 구축할 수 있다. 특히 API는 오픈AI의 리얼타임 API와 호환되는 웹소켓 방식을 지원한다. 기존 오픈AI API 이용자는 연결 주소와 모델명을 변경하는 방식으로 적용할 수 있다. 다만 출시 시점에는 웹RTC를 지원하지 않는다.
일레븐랩스 관계자는 “한국어를 포함한 90개 이상의 언어를 지원하는 일레븐 리얼타임을 통해 국내 기업과 개발자가 고객과 자연스럽게 소통하는 음성 에이전트를 구축하도록 지원하겠다”고 말했다.

[TITLE] 딥 프린시플, 일부 과학 평가서 GPT-6 아스트라 앞선 '하이드로젠' 공개
[LINK] https://www.aitimes.com/news/articleView.html?idxno=216967
[PUBLISHED] 2026-11-03 17:30 KST
[SOURCE] AI타임스
[TOPIC] 모델
[SCORE] 6
[REASON] 과학 특화 오픈웨이트 모델이 일부 평가에서 앞섬
[FIELD] AI 모델
[BODY]
중국 AI 소재 연구 전문 딥 프린시플(Deep Principle)이 실제 실험 기록과 연구 과정의 시행착오까지 학습한 과학 특화 AI 모델 '하이드로젠-1.0(Hydrogen-1.0)'을 공개했다. 총 7530억개 매개변수를 갖춘 오픈웨이트 모델로, 과학적 지식과 추론 능력을 넘어 실험 설계와 시뮬레이션, 신소재 탐색 등 여러 단계의 연구 작업을 수행하도록 설계했다.
딥 프린시플은 2일(현지시간) 하이드로젠-1.0을 공개하고 모델 가중치를 MIT 라이선스로 허깅페이스와 모델스코프에 배포했다.
Z.ai의 범용 모델 'GLM-5.3'을 기반으로 과학 분야 전문 지식과 자체 연구소의 실험 기록 등을 추가 학습했다. 전문가 혼합(MoE) 구조를 적용해 토큰당 약 400억개 매개변수만 활성화하며, 최대 100만 토큰의 문맥을 지원한다.
성능 평가에서는 일부 과학 연구 과제에서 최첨단 독점 모델을 앞섰다. 딥 프린시플 자체 평가에 따르면 과학 연구 역량을 측정하는 '프론티어사이언스-리서치(FrontierScience-Research·FSR)'에서 하이드로젠-1.0은 38.3%를 기록해 'GPT-6 아스트라'의 33.3%보다 5%포인트 높은 점수를 얻었다.
대학원 수준의 과학 지식을 평가하는 'GPQA 다이아몬드'에서도 기반 모델인 GLM-5.3보다 높은 성능을 보였으며, 오픈 모델인 '키미-K3'와 비슷한 수준을 기록했다.
실제 연구 환경을 반영한 내부 평가에서는 과학 컴퓨팅과 화학 반응 예측에서 GPT-6 아스트라를 각각 5.13%p, 4.76%p 앞섰다. 다만 핵자기공명(NMR)을 이용한 분자 구조 규명에서는 GPT-6 아스트라가 3.33%p 높은 점수를 기록했다.
이번 모델의 가장 큰 특징은 실제 연구 과정에서 축적한 성공과 실패의 기록을 학습했다는 점이다. 딥 프린시플은 화학·재료과학·생명과학 분야의 전문 지식과 연구진의 피드백, 전자연구노트(ELN), AI 에이전트의 연구 수행 기록을 활용했다.
특히 자체 연구 플랫폼 '미라(Mira)'를 통해 실험 목적과 절차, 관찰 결과, 후속 연구 방향을 연결한 데이터를 확보했다. 성공한 실험뿐 아니라 실패한 시도와 예상하지 못한 결과도 포함했다. 이를 통해 모델이 단순히 과학 문제의 정답을 찾는 데 그치지 않고, 실험 결과에 따라 다음 연구 방향을 결정하거나 잘못된 접근법을 수정하도록 학습시켰다. 지도 미세조정(SFT)과 강화학습(RL)을 결합해 연구 수행 능력을 높였다.
실제 시연에서도 여러 단계의 연구 작업을 수행했다. 재료과학 분야에서는 폴리에틸렌의 분자 구조를 구성하는 파이썬 코드를 작성하고 분자 동역학 시뮬레이션 도구인 GROMACS를 실행했다. 실행 과정에서 발생한 오류를 스스로 발견해 수정한 뒤 시뮬레이션을 다시 진행하고, 결과를 바탕으로 물질의 밀도와 분자 배열, 확산 특성 등을 분석했다.
실험실 자동화 작업에서는 12개 바이알을 이용하는 스즈키 커플링 화학 실험의 실행 절차를 생성했다. 가상 실험 환경에서 피펫 팁을 장착하지 않은 채 액체를 흡입하려는 오류를 발견하자 작업 순서를 수정해 검증을 마쳤다. 다만 실제 실험 장비를 작동한 것이 아니라 가상 환경에서 절차의 실행 가능성을 확인한 사례다.
신소재 탐색에서도 성과를 보였다. 전이금속 착물의 전자 에너지 차이를 최대화하는 과제에서 5차례에 걸쳐 후보 물질을 제안하고 평가 결과에 따라 탐색 방향을 수정했다. 최종 후보의 평균 에너지 차이는 4.318전자볼트(eV)로, GPT-6 아스트라의 3.689eV와 키미-K3의 3.353eV를 앞섰다. 딥 프린시플은 제한된 탐색 횟수 안에 연구 목표에 부합하는 후보 물질을 찾아내는 능력을 보여줬다고 설명했다. 다만 실제 새로운 물질의 합성이나 실험적 검증을 완료한 것은 아니다.
이번 공개는 과학 연구용 AI를 오픈웨이트로 제공한다는 점에서도 의미가 있다. 최근 오픈AI와 앤트로픽이 AI를 활용한 수학·생명과학 연구 성과를 발표했지만, 주요 모델은 독점적으로 운영하고 있다. 딥 프린시플은 연구자들이 모델을 직접 실행하고 수정할 수 있도록 가중치를 공개했다. 다만 전체 학습 데이터와 구체적인 학습 과정까지 공개한 것은 아니다.
실행 환경은 엔비디아와 AMD GPU를 모두 지원하며, 8개 GPU 구성에서 추론을 검증했다. SGLang을 이용해 오픈AI 호환 API 형태로도 실행할 수 있다.
